# Template development rules (ai_starter only)

These rules govern AI sessions developing the `ai_starter` template repository itself. In an instantiated project this file is template residue with no authority: `project-init`'s tailoring manifest deletes it; delete it by hand if init never ran.

- This repo IS the template: the whole tracked tree is the payload GitHub copies into new projects ("Use this template" / `gh repo create --template donohoo13/ai_starter`). There is no inner payload directory; editing any file is editing the product.
- Bracketed placeholders (the Company Overview line, `[project standards]`, Deployment, the `[project]` MCP stanzas) and stack sections for stacks absent here are shipped product content: leave them bracketed and intact — `project-init` resolves them in the destination, never a session here.
- This repo contains no application code and no UI: validation is `pnpm format:check` plus config parses (the `turbo` tasks no-op on the empty workspace), and the design docs (`UI_UX.md`, `BRAND_DESIGN.md`) are edited as shipped content under the context-file rules, not followed as this repo's own design system.
- Never run `project-init`, `sync-template`, or `template-feedback` here: init tailors instances and deletes template residue (this file included), sync pulls from this repo — it has no parent to pull from — and feedback files an instance's findings against this repo, which from inside is a grilling session and a fix rather than a queue entry. All three refuse on their own when they detect this repo; running them anyway wastes the detection.
- Every payload-affecting change lands with a `CHANGELOG.md` entry in the same change — what, why, and adaptation notes for diverged instances — and a release is a git tag (`vX.Y.Z`) on `main` matching the entry, published from `main` after the release PR merges as two separate commands, `git tag -a vX.Y.Z` first and `git push origin vX.Y.Z` second — the `guard-main` hook exempts publishing an existing tag from its default-branch push block precisely so this step stays reachable, while still refusing force, deletes, `--follow-tags`, and any ref that names a branch, and because it is a PreToolUse hook it evaluates state before the command runs, so batching creation and push into one call blocks on a tag that does not exist yet; instances consume the entry and the tag through `sync-template`, so an untagged or unlogged payload change is invisible to them.
- The template's own working artifacts (`docs/tasks/`, `docs/adr/`, `docs/designs/`, `docs/briefs/`, `CONTEXT.md`, `ARCHITECTURE.md`, `CHANGELOG.md`, this rules file) accrue here as normal project history; `project-init`'s manifest clears them in instances, so develop freely rather than self-censoring to keep the payload clean.
- Version references and cross-release provenance ("removed in vX.Y.Z", "since vX.Y.Z", "until vX.Y.Z") live only in the history records — `CHANGELOG.md` and the dated working artifacts under `docs/tasks/` and `docs/adr/` — never in the payload's present-tense steering docs (`CLAUDE.md`, `README.md`, every `.claude/skills/**` `SKILL.md` and reference, `UI_UX.md`/`BRAND_DESIGN.md`, `ARCHITECTURE.md`/`CONTEXT.md`, and hook comments); a change that removes or replaces a payload mechanism rewrites the affected steering doc to the mechanism that exists now and records the what, why, and when in its `CHANGELOG.md` entry, and anti-regression reasoning for a deleted mechanism is stated as current fact ("no hook enforces this, deliberately") without naming the release. Grep `v[0-9]` across the payload before tagging a release to catch leaks.
- Downstream propagation is pull-only: instances run their own `sync-template` sessions against this repo's changelog and tags; never push, PR, or hand-apply template changes into a child from a session here. Upstream reporting mirrors it: instances file findings into this repo's GitHub issue queue through `template-feedback`, and a session here consumes that queue as ordinary work — read the issue, verify its claim against the current payload (an instance reports against the version it carries, which may be several releases behind), then grill and fix. Never reach into a child to diagnose one of its issues.
- `.claude/settings.local.json` on this machine disables every shipped `.mcp.json` server except `context7` via `disabledMcpjsonServers` — template-dev sessions need none of the others, while the Context7-first docs rule binds sessions here too; keep that list in step when adding shipped server stanzas. Machine-personal quirks go in `CLAUDE.local.md` (gitignored, unversioned); rules that belong to the repo's process live in this file.
