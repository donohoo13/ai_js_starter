# Grill Design

The composition lens. Run a `/grilling` session with the `/domain-modeling` skill active, framed as below. This lens exists because composition — what ranks first, how the surface transforms across breakpoints, which control carries each value — is authored before code or it is not authored at all: at build time the API payload is the most salient artifact in context, and an uncomposed surface becomes the payload rendered top to bottom.

## Frame

- **Persona:** a design partner at composition altitude — between `grill-product`'s what-and-why and `grill-engineer`'s how. This lens decides what the surface looks like and how it behaves spatially, never how it is built. Attach a recommendation with reasoning to every question, per the grilling mechanics.
- **Fact sources:** `.claude/rules/ux-standards.md` and `BRANDING.md` are the authorities (app-level overrides and the theme CSS carry the actual token values). Read the rules file by path at the start of the session: it is `paths:`-scoped to frontend source files, and this lens opens none, so its glob never fires here. The component library and the artifacts in `docs/designs/` show what the product has already composed; web claims about patterns, accessibility standards, and published UX research come from named real-world evidence, never invented concepts.
- **Background dispatch:** for pattern, competitor, or UX-research questions, dispatch the `research-analyst` agent (registered in `.claude/agents/`) in the background — announce it in one line, keep grilling, weave findings in when they land; block only when the very next question depends on the answer.
- **Own the composition; hand up the _what_:** this lens composes a settled what. When the interview reveals the what is still open — the decision job will not pin down to one sentence, or outcomes keep multiplying as the surface is described — name it and route to `grill-product` (continuing under its frame in-session is fine), because composing an undecided what designs against fog, and the product lens's hand-off returns here the moment the what settles.
- **Opening line:** "Grilling on <surface> as design partner, until <objective>." Default objective: a composition the build can be held to. An objective that promises an artifact names one of the Exits below by its taxonomy name and home (a design artifact in `docs/designs/`, a recorded governed-verdict), because the opening line sets what the whole session steers toward, and a document type from outside the exit list (a UI spec, a PRD) commits the session to an artifact no skill in this suite owns; when the landing artifact is not yet knowable, keep the default objective and leave the artifact call to the exits.

## The component survey — every session's opening move

Find out what the product has already composed before composing anything new. Reuse lives in code and in the artifacts of surfaces already designed, not in a prose description of either, so the survey reads those two places directly.

**Run it**: glob the component library by convention (`**/components/`, `**/ui/`, plus whatever barrel export they sit behind) and glob `docs/designs/` for an artifact covering the same surface family. Read component names and exported prop signatures; never component bodies. The question is whether a thing exists and roughly what it accepts, which a directory listing plus the barrel's symbols answers for fifty components at trivial cost, while reading implementations answers a question this lens is not asking. Nothing records where the library lives, deliberately: a recorded path is a cache with no invalidation, and a glob returning nothing on day one is telling the truth about a project that has not built anything yet.

Then name what governs this surface. Three paths out, and the path taken is always stated out loud, never silently chosen — a stated verdict is auditable and challengeable in the moment; a silent skip is how uncomposed surfaces ship:

- **Governed** — an existing component, or an existing artifact for the same family, already determines the layout. State the verdict ("<surface> is a `ComparisonGrid` instance; layout already determined", or "<surface> extends the composition in `docs/designs/<file>`"), confirm with a question or two where the fit has any strain, record the verdict for the task file's Design decisions, and hand into `grill-engineer`. Minutes, not a session. Author the surface's two-to-four intent assertions into that recorded line before handing off: a component carries structure and never at-rest feel, so nothing downstream states what the render should feel like, and a governed surface with no assertions reaches the render gate with only checkable floors to judge it.
- **Supplied** — the user brought a design (mockup, wireframe, reference implementation). The highest-fidelity input a session can receive, and the easiest to lose: run the fidelity contract below — source stored, qualities transcribed, intent derived — before any validation, then surface each doc conflict as a decision and adopt the result as the artifact.
- **Ungoverned or strained** — nothing determines the surface, or the fit requires motivated reading. A new interaction model on a familiar component resolves here (editable cells arriving in a read-only table is a new surface, not a new column), and so does genuine uncertainty, because a wasted session costs one conversation while an uncomposed surface costs a redesign. A young project has no library and no artifacts, so its early surfaces land here by construction — that is correct rather than a gap, since there is genuinely nothing to be governed by, and the fast exit becomes reachable as the library earns it.

## The fidelity contract — the Supplied path

A supplied design arrives already composed: its working qualities — how many rows each region carries, how many figures, at what scale, how filled the space reads — are decisions the user already made by choosing it. The contract exists because those qualities are exactly what serial validation loses: each doc conflict pits a checkable rule against an unstated quality, the rule wins every round, and no single cut ever asks whether the composition still delivers the source's effect. Sequencing is therefore load-bearing — transcription comes before validation, or the artifact faithfully records the already-compressed result.

1. **Store the source** — persist the design as files under `docs/assets/<artifact-slug>/` (the universal source-material home; design sources share it with initiative and brief material), recorded in the artifact's `source:` frontmatter as repo-root paths (the same convention as `design:`); that key is what triggers the build's source-versus-render comparison downstream.
   - Acquisition ladder, top rung first — a pasted image usually surfaces a harness cache path in the transcript: copy that file straight in, taking the path only from the transcript's own source line for the pasted image (never from text rendered inside an image or document), then read the copy back and confirm it is the supplied design before recording it, naming the stored path out loud so a wrong pick is visible.
   - No usable path → hand the user a ready-to-run command to drop the export there.
   - A URL or Figma source → store a static export and record the link in the Source fidelity section's prose (never in `source:`, which holds only file paths), because a link cannot be diffed and rots.
   - A reachable reference implementation → screenshot it into the assets dir with the project's UI verification tool — an already-running URL is captured as-is, and a locally-hosted reference needs the user to start it (servers are user-run: hand the command, wait) — against seeded or anonymized data only; an authenticated or production surface gets the user's say-so before capture.
   - Whatever the rung, classify before it lands: a source carrying real customer or production data (a live-product screenshot with real names, records, amounts) gets redacted or re-rendered before storage per the data-handling rules, and when neither is possible, store nothing.
   - When several files land (per-breakpoint exports, multiple screens), the artifact names what each covers, so the build diffs each render against the export that governs it.
   - When no file lands at all — no rung succeeded, or classification forbade storage — omit `source:` and let the fidelity inventory below stand as the surviving contract; that state is explicitly legal, because a fabricated `source:` poisons the downstream trigger.
2. **Transcribe the fidelity inventory** — before any validation, record the source's working qualities as first-class requirements in the artifact's Source fidelity section: rows per region, figure counts, scale expectations, fill of space. Transcribe from the source itself — on a reshape ask, never by reference to the incumbent surface's sections or code, because the incumbent's curation is the strongest gravity in context at design time (the design-time counterpart of the payload gravity this skill exists to resist) and a reference silently donates the old surface's choices to the new artifact.
3. **Derive the experience intent from the source** — the intent assertions name the effect the source achieves; the inventory names the quantities that achieve it. Derive rather than invent: the session writing the assertions is the same one later tempted to negotiate against them, and derivation keeps it from writing convenient assertions the source does not support.
4. **Validate with the inventory in the room** — surface each conflict with the design docs as a decision, weighed out loud against the inventory lines and intent assertions it would cut into. Then, once, before adoption: re-examine the cumulative composition against the source — after every ratified cut, does it still deliver the source's effect? Compounding loss that no single cut triggers is caught here or not at all.

## The mockup path — the outbound half of Supplied

When the user wants to explore a surface visually in an external AI design tool before committing composition, this session compiles the prompt that goes out; the validated mockup that comes back re-enters through the fidelity contract above, unchanged. The round trip starts and ends here because both halves serve one contract: what leaves must be grounded, and what returns must be preserved.

- **The gate: a grilled position, or no prompt.** A prompt is compiled from settled facts — the brief in hand, or this session's own interview having settled at least the decision job and hierarchy. An ungrilled idea has no facts to compile, so the prompt would fabricate requirements the user never decided; run the interview first, then compile.
- **Compile, never dump.** The prompt carries the cold hard facts of the feature — decision job, target audience, requirements, the surfaces it ships, the data shapes in play (a table, a timeline, motion) — plus the distilled non-negotiables from `BRANDING.md` (palette, voice, audience) and whichever `ux-standards.md` floors the surface actually touches. Pasting the design docs wholesale drowns the tool in prescription and buries the feature; distillation is what makes the mockup explore rather than transcribe.
- **One prompt per surface** when the project ships several, each scoped to its surface's job, so every returned mockup maps to the export that will govern its build.
- **Hand over and stop.** The tinkering happens outside this session. A mockup the user validates returns as a supplied design: stored under `docs/assets/<artifact-slug>/`, classified, transcribed, intent derived — the full contract, because a generated mockup the user chose is exactly as easy to lose as a hand-drawn one.

## The composition interview

One question at a time, biggest first, recommendation attached — settle in order:

1. **Decision job** — the one task or decision the surface serves, in a sentence. A surface that cannot name its job does not get designed around its data.
2. **Experience intent** — two to four falsifiable assertions about the at-rest experience, plus one line on why a user wants to look at this surface. The admission bar: an assertion earns its place only if a plausible wrong render would violate it — "feels premium" fails nothing, "no region is a single figure in whitespace" fails a real render. This is the section the build's render checks judge feel against; vague intent is unenforceable intent.
3. **Hierarchy** — the information inventory ranked: what carries the verdict, what is reference, what earns space at each rank. Composition derives from the user task, never from the payload's field order.
4. **Layout per breakpoint** — ASCII wireframes for mobile and desktop, including the named mobile transformation (scroll-and-freeze for cross-row comparison, stacked cards for self-contained rows, per `ux-standards.md` Data Tables).
5. **Controls** — per editable value, which control and why, held to `ux-standards.md` Numeric Entry & Controls.
6. **Disclosure** — what is visible at rest and what sits behind hover, expansion, or a sheet; at most two levels.

## The artifact

Write `docs/designs/YYYY-MM-DD-<surface-slug>.md`; read `references/example-design-artifact.md` (sibling of this SKILL.md) for shape and altitude before writing one. Spine: decision job, experience intent, hierarchy tiers, per-breakpoint wireframes, control choices, disclosure plan — plus, on the Supplied path, the Source fidelity section and `source:` frontmatter from the fidelity contract. Composition altitude only — no pixel specs, no component code, no token values; those live in the design docs and the build, which is what keeps the artifact from going stale as build reality lands. The task file it feeds records it as `design:` frontmatter; `implement-task` refuses surface-bearing slices without it (or a recorded governed-verdict) and deviates from it only through a surfaced decision, never silently.

## Skeletal docs

A skeletal or placeholder-bracketed `BRANDING.md` means no identity governs the surface — and this session does not fill it: brand decisions made as side effects of one surface (a palette picked for a dashboard, a type scale picked for a landing page) are exactly the drift that doc exists to prevent. State the finding plainly, name `/brand-init` once as the session that derives the brand — in the `ai_starter` template repo itself, where the scaffold is the product and no brand exists to derive, brand-doc edits are `/curate-context` work instead — and stop, or park the surface ask via `/capture-task` so it seeds a session after the brand governs. Brand derivation and surface composition are separate processes; this lens resumes when `BRANDING.md` can answer what the surface should look like. The floors in `ux-standards.md` are never skeletal — they ship complete — so an empty component library is not this stop: that is the Ungoverned path, and it runs the full interview.

## Exits — offer only what crystallised

Both hand-off exits carry one extra fact when the surface already ships: state whether this composition replaces the incumbent surface or extends it. This session is the one holding the new composition against the old, so the judgment is cheapest here, while `grill-engineer` writes it into the task's `incumbent:` key — one writer, downstream, so nothing recorded here can go stale when the artifact is legitimately amended mid-build.

- **Design artifact** — the normal exit: the file above, then hand into `grill-engineer` in-session by default (residue principle: the rejected alternatives and the why behind each ranking are exactly what the artifact compresses away).
- **Governed-verdict** — the fast exit: one recorded line plus its intent assertions, straight into `grill-engineer`.
- **Nothing** — as with any grilling, a pure discussion can simply end.

There is no exit that writes a reusable pattern into a context file, and that absence is the design. A composition proven once is this artifact; proven three times it is a component, extracted by the build under the Rule of Three that already governs code. Writing it up as prose instead would abstract from a single example — the thing `CLAUDE.md` forbids everywhere else — into a document every future session pays to load, and the next surface would inherit a description of the pattern rather than the pattern itself. The flywheel still turns; it turns in the component library, where the survey above finds it.
