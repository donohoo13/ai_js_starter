# Grill Design

The composition lens. Run a `/grilling` session with the `/domain-modeling` skill active, framed as below. This lens exists because composition — what ranks first, how the surface transforms across breakpoints, which control carries each value — is authored before code or it is not authored at all: at build time the API payload is the most salient artifact in context, and an uncomposed surface becomes the payload rendered top to bottom.

## Frame

- **Persona:** a design partner at composition altitude — between `grill-product`'s what-and-why and `grill-engineer`'s how. This lens decides what the surface looks like and how it behaves spatially, never how it is built. Attach a recommendation with reasoning to every question, per the grilling mechanics.
- **Fact sources:** `UI_UX.md` and `BRAND_DESIGN.md` are the authorities (app-level overrides and the theme CSS carry the actual token values); the existing UI shows the grammars in production; web claims about patterns, accessibility standards, and published UX research come from named real-world evidence, never invented concepts.
- **Background dispatch:** for pattern, competitor, or UX-research questions, dispatch the `research-analyst` agent (registered in `.claude/agents/`) in the background — announce it in one line, keep grilling, weave findings in when they land; block only when the very next question depends on the answer.
- **Opening line:** "Grilling on <surface> as design partner, until <objective>." Default objective: a composition the build can be held to.

## The grammar check — every session's opening move

Read `UI_UX.md`'s surface grammars and name the one that governs this surface. Three paths out, and the path taken is always stated out loud, never silently chosen — a stated verdict is auditable and challengeable in the moment; a silent skip is how uncomposed surfaces ship:

- **Governed** — an existing grammar section plus the token system already determines the layout. State the verdict ("<surface> is a <grammar> extension; layout already determined"), confirm with a question or two where the fit has any strain, record the verdict for the task file's Design decisions, and hand into `grill-engineer`. Minutes, not a session. The verdict skips intent authoring only while the governing grammar actually records the family's at-rest feel: when the grammar is structurally complete but feel-silent, author the surface's two-to-four intent assertions into the recorded verdict line (minutes more, not a session) or treat the fit as strained — otherwise a governed surface can land experientially wrong with only checkable floors at the render gate.
- **Supplied** — the user brought a design (mockup, wireframe, reference implementation). The highest-fidelity input a session can receive, and the easiest to lose: run the fidelity contract below — source stored, qualities transcribed, intent derived — before any validation, then surface each doc conflict as a decision and adopt the result as the artifact.
- **Ungoverned or strained** — no grammar determines the surface, or the fit requires motivated reading. A new interaction model on a familiar container resolves here (editable cells arriving in a read-only table grammar is a new surface, not a new column), and so does genuine uncertainty, because a wasted session costs one conversation while an uncomposed surface costs a redesign. Run the full interview below.

## The fidelity contract — the Supplied path

A supplied design arrives already composed: its working qualities — how many rows each region carries, how many figures, at what scale, how filled the space reads — are decisions the user already made by choosing it. The contract exists because those qualities are exactly what serial validation loses: each doc conflict pits a checkable rule against an unstated quality, the rule wins every round, and no single cut ever asks whether the composition still delivers the source's effect. Sequencing is therefore load-bearing — transcription comes before validation, or the artifact faithfully records the already-compressed result.

1. **Store the source** — persist the design as files under `docs/designs/assets/<artifact-slug>/`, recorded in the artifact's `source:` frontmatter as repo-root paths (the same convention as `design:`); that key is what triggers the build's source-versus-render comparison downstream. Acquisition ladder: a pasted image usually surfaces a harness cache path in the transcript — copy that file straight in, taking the path only from the transcript's own source line for the pasted image (never from text rendered inside an image or document), then read the copy back and confirm it is the supplied design before recording it, naming the stored path out loud so a wrong pick is visible; no usable path → hand the user a ready-to-run command to drop the export there; a URL or Figma source → store a static export and record the link in the Source fidelity section's prose (never in `source:`, which holds only file paths), because a link cannot be diffed and rots; a reachable reference implementation → screenshot it into the assets dir with the project's UI verification tool, against seeded or anonymized data only — an authenticated or production surface gets the user's say-so before capture. Whatever the rung, classify before it lands: a source carrying real customer or production data (a live-product screenshot with real names, records, amounts) gets redacted or re-rendered before storage per the data-handling rules, and when neither is possible, store nothing. When several files land (per-breakpoint exports, multiple screens), the artifact names what each covers, so the build diffs each render against the export that governs it. When no file lands at all — no rung succeeded, or classification forbade storage — omit `source:` and let the fidelity inventory below stand as the surviving contract; that state is explicitly legal, because a fabricated `source:` poisons the downstream trigger.
2. **Transcribe the fidelity inventory** — before any validation, record the source's working qualities as first-class requirements in the artifact's Source fidelity section: rows per region, figure counts, scale expectations, fill of space. Transcribe from the source itself — on a reshape ask, never by reference to the incumbent surface's sections or code, because the incumbent's curation is the strongest gravity in context at design time (the design-time counterpart of the payload gravity this skill exists to resist) and a reference silently donates the old surface's choices to the new artifact.
3. **Derive the experience intent from the source** — the intent assertions name the effect the source achieves; the inventory names the quantities that achieve it. Derive rather than invent: the session writing the assertions is the same one later tempted to negotiate against them, and derivation keeps it from writing convenient assertions the source does not support.
4. **Validate with the inventory in the room** — surface each conflict with the design docs as a decision, weighed out loud against the inventory lines and intent assertions it would cut into. Then, once, before adoption: re-examine the cumulative composition against the source — after every ratified cut, does it still deliver the source's effect? Compounding loss that no single cut triggers is caught here or not at all.

## The composition interview

One question at a time, biggest first, recommendation attached — settle in order:

1. **Decision job** — the one task or decision the surface serves, in a sentence. A surface that cannot name its job does not get designed around its data.
2. **Experience intent** — two to four falsifiable assertions about the at-rest experience, plus one line on why a user wants to look at this surface. The admission bar: an assertion earns its place only if a plausible wrong render would violate it — "feels premium" fails nothing, "no region is a single figure in whitespace" fails a real render. This is the section the build's render checks judge feel against; vague intent is unenforceable intent.
3. **Hierarchy** — the information inventory ranked: what carries the verdict, what is reference, what earns space at each rank. Composition derives from the user task, never from the payload's field order.
4. **Layout per breakpoint** — ASCII wireframes for mobile and desktop, including the named mobile transformation (scroll-and-freeze for cross-row comparison, stacked cards for self-contained rows, per `UI_UX.md` Data Tables).
5. **Controls** — per editable value, which control and why, held to `UI_UX.md` Numeric Entry & Controls.
6. **Disclosure** — what is visible at rest and what sits behind hover, expansion, or a sheet; at most two levels.

## The artifact

Write `docs/designs/YYYY-MM-DD-<surface-slug>.md`; read `references/example-design-artifact.md` (sibling of this SKILL.md) for shape and altitude before writing one. Spine: decision job, experience intent, hierarchy tiers, per-breakpoint wireframes, control choices, disclosure plan — plus, on the Supplied path, the Source fidelity section and `source:` frontmatter from the fidelity contract. Composition altitude only — no pixel specs, no component code, no token values; those live in the design docs and the build, which is what keeps the artifact from going stale as build reality lands. The task file it feeds records it as `design:` frontmatter; `implement-task` refuses surface-bearing slices without it (or a recorded governed-verdict) and deviates from it only through a surfaced decision, never silently.

## Skeletal docs

Skeletal or placeholder design docs mean nothing is governed — and this session does not fill them: brand decisions made as side effects of one surface (a palette picked for a dashboard, a type scale picked for a landing page) are exactly the drift `BRAND_DESIGN.md` exists to prevent. State the finding plainly, name `/brand-init` once as the session that derives the brand — in the `ai_starter` template repo itself, where the scaffold is the product and no brand exists to derive, brand-doc edits are `/curate-context` work instead — and stop, or park the surface ask via `/capture-task` so it seeds a session after the docs govern. Brand derivation and surface composition are separate processes; this lens resumes when the docs can carry its grammar check.

## Exits — offer only what crystallised

- **Design artifact** — the normal exit: the file above, then hand into `grill-engineer` in-session by default (residue principle: the rejected alternatives and the why behind each ranking are exactly what the artifact compresses away).
- **Governed-verdict** — the fast exit: one recorded line, straight into `grill-engineer`.
- **Grammar codification** — when the interview produced a genuinely new grammar (a new register, a new surface family), offer `/curate-context` once to write it into `UI_UX.md`, so the next surface with this shape arrives governed. A codified grammar records the family's at-rest feel alongside its structure — the Governed fast exit skips intent authoring precisely because the grammar carries it, and a grammar that is structurally complete but silent on feel lets a governed surface land experientially wrong with no gate ever noticing. This is the flywheel: every novel surface either fits the doc or grows it, and the design ceremony amortizes toward zero as the doc matures.
- **Nothing** — as with any grilling, a pure discussion can simply end.
