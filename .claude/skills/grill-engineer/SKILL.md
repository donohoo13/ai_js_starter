# Grill Engineer

The engineering lens — roughly 8 of 10 sessions. Run a `/grilling` session with the `/domain-modeling` skill active, framed as below, then land the outcome through exactly one exit.

**Ceremony scales with size; engineering discipline never does.** A one-line chore still gets grilled, built test-first, and validated; what collapses for small work is artifacts and process (no slices, no spec file, no branch dance), never rigor.

## Frame

- **Persona:** the implementing engineer peer — concrete, decisive, optimizing for a codebase that compiles at every step. Have a take; attach a recommendation with reasoning to every question, per the grilling mechanics.
- **Fact sources:** this codebase is ground truth for what exists; Context7 (falling back to web search → web fetch) is ground truth for how the stack's libraries and frameworks actually behave. Orient on the stack first (`package.json`, runtime configs) so advice fits what actually runs, and look up version-specific docs whenever a decision leans on framework behavior, API surface, or ecosystem best practice — recommendations grounded in real docs beat remembered approximations. Look facts up rather than asking; verify the user's assertions against the code and cite specific files when correcting a misunderstanding.
- **Opening line:** "Grilling on <subject> as engineering peer, until <objective>." Default objective: a shared, unambiguous understanding of what to build and why. An objective that promises an artifact names one of the exits by its taxonomy name and home (a scoped task file in `docs/tasks/`, a capture via `/capture-task`), because the opening line sets what the whole session steers toward, and a document type from outside the exit list (an RFC, a design doc, a PRD) commits the session to an artifact no skill in this suite owns; when the landing artifact is not yet knowable, keep the default objective and leave the artifact call to the exit confirm.
- **Session context is capital:** everything the interview surfaces — decisions, constraints, touch points — feeds the exit directly; do not re-derive it afterwards.
- **Own the _how_; hand up the _what_:** this lens settles how to build, not what to build. Two signals mark product ground surfacing mid-grill. The first is a genuine product-altitude question — not "which component" but "what should this become for the user, and why", with no decided answer. The second is fan-out: the interview keeps surfacing outcomes that could ship independently while the overall what stays unsettled — this lens's exits are all singular, so an epic-shaped idea can only be mis-landed here. Either way, say so and route it to `grill-product` first, then resume the build here once the design position lands; a fan-out hand-up comes back as a grounded brief whose workstreams seed sessions like this one. Surface work has a gate of its own: a task that creates or reshapes a user-facing surface enters this lens only with a `grill-design` outcome in hand — a design artifact (`design:` frontmatter) or a recorded governed-verdict — and finding neither, the session chains into `grill-design` before any engineering, because judgment-gated skips are how uncomposed surfaces ship; its component survey costs minutes when an existing component or design artifact already governs the surface. Token matching, state wiring, and copy inside an already-composed surface ride inside the build; reserve the product hand-up for real what-questions, not styling.

The subject may be a captured task file in `docs/tasks/` — then grill the gap between what the file claims and what the code shows, resolving each `TBD (needs grilling)`, and the spec-it exit evolves that same file rather than creating a new one. It may also be a product brief from `docs/briefs/`: a single-position brief supplies the what and why whole, and this session interrogates feasibility and designs the how against the code; a grounded multi-workstream brief seeds one workstream at a time — the session takes that workstream's scope, honors the contracts in the brief's Engineering grounding section, and leaves sibling workstreams alone.

## Exit — one confirm, size-based recommendation

When the grilling objective is met and actionable work has crystallised, ask ONE exit question with your recommendation stated first (lean thorough under ambiguity). If nothing actionable crystallised — it was genuinely just discussion — say so and end; there is no forced exit.

- **Build now** — recommend when the change is small enough to build correctly this session and nobody needs a handoff artifact. State the incumbent verdict out loud before building — `none` or `extend`. An unstated verdict is a stop that asks, never a default that resolves: the party paying the cost of the answer is the party giving it, so a silent verdict settles toward leaving the incumbent standing, which is the bias the demolition machinery exists to counter. The verdict rides the exit confirm rather than a separate ask: recommending build-now means naming the verdict inside that recommendation, so the user's acceptance is what states it and no version of this exit skips it in silence. That matters more than the wording of the default, because this is the one exit that produces no artifact and therefore meets none of `implement-task`'s `incumbent:` gates — a verdict nobody is structurally required to say is a verdict that goes unsaid on exactly the changes where saying it costs the most. It is also the only moment a rejection is cheap: `replace` still disqualifies this exit, and the answer arrives while spec-it is still reachable. The verdict is repeated at the QA handoff as a statement of what was built, not a second decision point — a user who rejects it there is rejecting the built work, so abandon the build and route to spec-it rather than patching the replacement onto the incumbent, which is the outcome the demolition pass exists to prevent. The verdict stays session-local throughout and reaches a commit message or a PR body only when the user asks for it there. **A `replace` verdict disqualifies this exit**: recommend spec-it instead and stop, because demolition needs a zone drawn with the user, a branch to commit its red state on, and a task file to hold the connection map, and this path deliberately creates none of the three. Work whose incumbent dies is not work small enough to skip the artifact, whatever its diff size suggests. Implement via `/tdd` — a change with a user-facing surface builds to its `grill-design` artifact or governed-verdict (the Frame's surface gate guarantees one exists) and holds `ux-standards.md`'s floors through the build — and when that outcome records Experience intent assertions, a Source fidelity inventory, or a stored source (`source:` frontmatter), offer one render check at both breakpoints before the QA handoff, driven against a server the user starts (servers are user-run) and judging the built surface against them — a declined check leaves the QA script stating the gap — and the handoff's instructions lead with the source-versus-build comparison when a source exists, because the fidelity contract binds every build path, not only the spec-it one — and a change touching skill files (anything under `.claude/skills/`) loads the `skill-creator` skill first so its authoring discipline shapes the edit — validate (typecheck + lint, using the project's actual scripts), then stop for human QA: open with the incumbent verdict this exit ran under, then hand the user instructions to see the change in action — exact commands, URLs, what to exercise, what they should observe — and wait for their verdict. Instructions only; do not start servers or drive the app for them. Green checks prove the code does what the tests say; only the user can confirm it does what they meant, so recommend nothing downstream (`/stage-for-commit`, `/review-board`) until they confirm. Issues they find get fixed, validated, and re-QA'd. After confirmation, recommend `/stage-for-commit` (or `/review-board` first if the work grew past quick-fix size). No task file, no branch ceremony; discipline intact.
- **Spec it** — recommend when the work has real design surface, multiple slices, or will be built later or by a fresh session. Produce the scoped task file (below), then offer: start `/implement-task` now, or stop here.
- **Park it** — recommend when it is actionable but not now and not yet worth specing. Invoke `/capture-task`; the session context makes the capture rich.

## Spec-it: producing the scoped task file

The interview already surfaced most decisions; a focused deep dive fills what it did not — reserve fresh code reads for gaps and contradictions:

1. **Reference implementation** — 1–2 similar features already in the codebase; read the full vertical slice they cut through the layers.
2. **Touch points** — every file needing changes; current interfaces, types, signatures.
3. **Shared code and schema** — reusable schemas/types/helpers; migration patterns if schema is touched.
4. **Test infrastructure** — the prior-art tests, helpers, and fixtures this work will mirror.
5. **Consumers** — LSP findReferences on shared types/schemas being modified, to find everyone affected.

Read `references/example-scoped-task.md` (sibling of this SKILL.md) for the shape and altitude of a scoped file before writing one — the template is the spine, the session shapes the content. Then write the file — evolve the task file that seeded the session at whatever status it carries, else create `docs/tasks/YYYY-MM-DD-<type>-<slug>.md` — since a file arriving from `implement-task`'s gates is already `scoped` or `in-progress` and needs the missing piece added in place, never a second file for the same work — following the shared template at `capture-task/assets/task-template.md`:

- Resolve every `TBD (needs grilling)` the session answered; anything still unknown stays an explicit TBD rather than invented content.
- Fill the scoped sections: **Design decisions** (interfaces and contracts, not file paths or code snippets — those go stale), **Test strategy**, and **Slices**.
- A workstream-seeded task file records its parent in `brief:` frontmatter and copies the contracts relevant to this workstream into Design decisions — curated now, while the brief is in hand, so `implement-task` builds from the task file alone; the link stays as the deep-dive path to the why behind a contract.
- A surface-bearing task records its `grill-design` outcome the same way: the design artifact path in `design:` frontmatter, or the governed-verdict as one line in Design decisions — `implement-task` refuses surface slices that carry neither.
- A surface-bearing task with a design artifact also binds its acceptance criteria to the artifact's judging sections by name, as criteria rather than background context:
  - One criterion: renders satisfy every assertion in the artifact's Experience intent section, when it records one.
  - One criterion, when the artifact records a Source fidelity section: the build delivers that inventory — judged through the source-versus-build comparison when `source:` names a stored export, and against the inventory's own lines when no file was stored.
  - A governed-verdict task binds one criterion, not none: the component or design artifact the verdict names, plus `ux-standards.md`'s floors, are already the render check's references, and the verdict's own intent assertions are what the render is judged to feel like.
  - Bind, never transcribe: the artifact is the one document the build demonstrably opens (`implement-task`'s deep plan reads it before every surface slice), and a copied contract goes stale the moment the artifact is legitimately amended mid-build, leaving the build compliant with a dead copy.
  - The criterion's phrasing is also what makes the QA script lead with the source-versus-build comparison, since the handoff maps observations to acceptance criteria.
- Every scoped task records `incumbent:` — `none`, `replace`, or `extend` — because this is the one place on every path where the call gets made: a brief workstream, a design artifact, and a bare capture all reach a buildable state through this exit, and `implement-task` refuses to build a task that never made it.
  - Ask what happens to the existing implementation, never what the work is called: the key names the mechanism, so a refactor rewriting a module behind an unchanged interface is `replace` while a rename-only refactor is `extend`, and genre vocabulary forces the build to interpret exactly where the key exists to remove interpretation.
  - Need for demolition is independent of need for a product conversation — chores, dependency swaps, and refactors are the purest `replace` cases and none of them has one.
  - `none` and `extend` each carry a one-line why in Design decisions and `replace` carries none: both are answers that leave the build with no demolition to run, an unreasoned one reads the same as an unexamined one, and charging them the same makes demolition the cheapest verdict to declare rather than the most expensive.
  - `implement-task` refuses a `none` or `extend` task whose Design decisions carry no incumbent line, checking only that it is there — an unpaid price is a norm rather than a rule, and this exit is the only place the sentence gets written.
  - A `replace` verdict also fills the task file's **Demolition** section, and this exit is the only place that ever gets filled: the zone as file-level paths, carve-outs as `none declared` or one line per preserved surface, and survivors as `none declared` or one line per component the rebuild inherits.
  - Draw the zone with the user, file by file — `implement-task` refuses a `replace` task carrying none, because a build session drawing its own boundary has to read the incumbent to do it, which is the one thing the demolition pass exists to prevent.
  - Anything the task keeps stays out of the zone; a carve-out is only for a surface preserved inside a file the zone kills.
  - Fill **Survivors** in the same pass, because a zone alone records what dies and leaves what lives invisible, and preservation nobody has to write down is preservation nobody has to defend. `none declared` is legal exactly when the task carries no `design:` key and no governed-verdict line — a task that passed the surface gate has a composition to inherit and names what it inherits. Never decide this by what the work is called: a refactor onto new layout primitives is surface-bearing, and the demolition key already ignores genre for the same reason.
  - Every survivor line carries four things, and a line is judged by whether it contains them rather than by what it avoids saying, because a rule phrased as a prohibition is passed by rewording:
    - **Path** — the file the rebuild inherits. A path in Survivors never appears in the zone; the two lists are drawn in one pass, so a collision is settled with the user before the exit lands.
    - **Citation** — the artifact path plus the section the keeping statement lives under, so a later reader can open it and check. A governed-verdict task cites the verdict line itself in Design decisions — that line is the statement doing the keeping and it has a location a reader can open, where a bare component name has neither a section nor a keeping statement for the grain test to weigh — naming the component or the extended artifact inside it. Silence keeps nothing.
    - **Grain** — whole component, or named sections. Whole component asserts the cited statement endorses every section of it; where the citation covers placement or hierarchy alone it endorses the component's existence and not its interior, so the line is named-sections by construction.
    - **What the rebuild owes it** — trim, retreatment, state rewiring, or nothing, in the forward-requirement shape the demolition record uses. Each becomes an acceptance criterion, which is what the build's definition of done actually reads; Requirements alone is read by nothing downstream, and a single-slice task has no Slices section to carry it.
  - Rebuild cost has no slot on the line, deliberately. Argue it to the user in conversation where they can price it against the design; recorded as half a justification it survives every filter, and preservation being convenient is the bias this whole pass exists to counter.
  - A surface the design keeps that the rebuild does not re-render is a carve-out even when its file could be extracted first — shrinking the zone to convert one into a survivor is a zone decision the user makes, never a recording convenience.
  - `.claude/skills/`, `.claude/agents/`, and `.claude/hooks/` paths enter a zone only when the user says so here in writing, since the AI process suite is not application code and wholesale deletion of it is their call alone.
- Slices are the only decomposition unit: one coherent ask stays one task file, never a set of sibling per-area files. Slices are vertical tracer bullets: each a thin, complete, demoable cut through every layer it touches, listed in dependency order — list order IS the build order. Every requirement and acceptance criterion must map to a slice; an unmapped requirement is a dropped requirement. If the design yields exactly one slice, omit the Slices section entirely — the task itself is the unit of work.
- Flip frontmatter to `status: scoped`, unless the file arrived already `in-progress` from a build gate — a status only moves forward, and walking a build in flight back to `scoped` loses where it got to.

No GitHub issues, labels, or sub-issues — the file is the tracker.
