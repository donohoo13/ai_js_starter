# Fork points — where the suite couples to tools and conventions

The maintained map of every place the shipped suite assumes a platform, tool, or convention. `project-init` reads this during detection instead of re-deriving the suite's anatomy in every project; the drift greps at the bottom catch anything this file has fallen behind on. Maintenance contract: any edit to a skill, agent, hook, or shipped config that changes a coupling below updates this file in the same change.

Each entry: what the artifact assumes today → the tailoring lever when the project differs.

## Git platform (shipped assumption: GitHub + `gh`)

- `ship-pr/SKILL.md` — the deepest coupling: description and body say "GitHub PR", mechanics run `gh pr create --title --body --base <default-branch>`, structure comes from `.github/PULL_REQUEST_TEMPLATE.md` (auto-loaded at invocation by a `cat` bang command, scaffolded on first use if absent), and the routed-around failure mode is described as "a bare `gh pr create`". → GitLab: `glab mr create`, `.gitlab/merge_request_templates/`, PR→MR vocabulary throughout; other platforms: their CLI; no remote or solo-on-main: consider removing the skill and its README entry entirely.
- `review-board/SKILL.md` — PR-number scoping uses `gh pr diff <n>` / `gh pr view <n>`. → swap for the platform CLI equivalents.
- `CLAUDE.md` (shipped) Git Control section — "CLI tools (like `gh` for GitHub)". → name the real platform and CLI.
- `.claude/settings.json` — `deny` entries hardcode pushes to `main`. → rename if the default branch differs; drop if the team commits to main by design.
- `template-feedback/SKILL.md` — **the inverted case: leave its `gh` calls alone.** Every other entry in this section couples to the _instance's_ platform; this skill's `gh issue list` / `gh issue create` target the _template's_ repo, which stays on GitHub no matter where the instance lives. Retargeting it to a GitLab project's own `glab` severs the feedback channel silently — issues would file against the instance instead of the template, and nobody notices until the template's queue is inexplicably empty. → tailor only if the template itself moves platforms or is forked to a new home, in which case the repo reference changes in lockstep with `sync-template`'s remote; a project that wants no feedback channel deletes the skill, its README section, and its stage-map row together.

## Task tracker (shipped assumption: the file is the tracker)

- `capture-task/SKILL.md` — captures land in `docs/tasks/YYYY-MM-DD-<type>-<slug>.md`; explicitly never creates platform issues. → with Linear/Jira: decide where captures land (in-repo file stays the recommended default; mirroring to the tracker with agreed team/project/labels is the common compromise) and rewrite the capture destination and description accordingly.
- `implement-task/SKILL.md` — reads `scoped` files from `docs/tasks/`, carries status frontmatter `scoped → in-progress → done`, dynamic context greps `docs/tasks/*.md`. → if scoped work lives in the tracker, define how a task file is seeded from a tracker issue (recommend the file remains the build artifact; the tracker links to it).
- `grill-engineer/SKILL.md` — spec-it exit writes `docs/tasks/`; product briefs seed from `docs/briefs/`. → decide whether scoped task files and briefs also post to the tracker, and to which project/team.
- `ground-brief/SKILL.md`, `grill-product/SKILL.md` — multi-workstream briefs live at `docs/briefs/` with `status: draft|grounded` frontmatter; ground-brief appends the Engineering grounding section, and workstream entries link `docs/tasks/` files (which back-link via `brief:` frontmatter). → if scoped task files and briefs post to a tracker, decide where grounded briefs and their workstream links live there too.
- `grill-design/SKILL.md` — design artifacts land in `docs/designs/YYYY-MM-DD-<slug>.md`, task files back-link via `design:` frontmatter (task template + implement-task's surface gate), and supplied source designs (including validated external-tool mockups from the mockup path) store as static exports under `docs/assets/<artifact-slug>/` — the universal source-material home shared with initiative and brief material — recorded in `source:` frontmatter, which triggers implement-task's source-versus-render comparison. → if design artifacts live elsewhere (Figma, tracker attachments), keep the in-repo file as the build contract and link out from it — and keep static source exports in-repo where posture allows, because the render comparison needs a file to open and a link cannot be diffed; under a compliance regime, or when sources routinely carry customer data, retarget the assets dir to a gitignored path with out-of-band sharing, accepting that the source comparison then runs only on machines holding the assets.
- `grill-initiative/SKILL.md` + `grill-me/SKILL.md` file-seeded routing — initiative docs live at `docs/initiatives/YYYY-MM-DD-<slug>.md` (Direction + Portfolio), briefs back-link via `initiative:` frontmatter, raw source material stores verbatim under `docs/assets/<slug>/`, and `/grill-me @<file>` routes by artifact kind and status frontmatter. → with an external tracker holding initiatives/projects (Linear initiatives, Jira epics), decide whether the in-repo initiative doc remains the direction authority with the tracker mirroring the portfolio (recommended — the Direction section has no tracker equivalent), and keep the file-seeded routing table aligned with wherever lifecycle status actually lives.
- `ship-pr/SKILL.md` — QA evidence reads `docs/tasks/` status. → keep aligned with wherever task status actually lives.
- `review-board/SKILL.md` — Step 3 sends the two deferrable finding kinds (a pre-existing bug needing investigation, a design tradeoff needing its own decision) to `/capture-task`, and the record commit is where every other outcome lives. → if captures land in a tracker, name that destination in Step 3 so a deferred finding reaches the same place every other capture does.
- `.claude/skills/README.md` — "No GitHub issues anywhere in the chain — the file is the tracker." → restate to match the agreed structure.
- ADRs (`docs/adr/`) stay in repo regardless of tracker; recommend against moving them. The status and relation frontmatter from `domain-modeling/ADR-FORMAT.md` is held by that skill's discipline and assumes `NNNN-slug.md` numbering; no hook checks it. → projects whose ADRs live at another path (`decisions/`, `doc/adr/`) retarget the path in `ADR-FORMAT.md` and in `domain-modeling`'s description; a project wanting the frontmatter checked mechanically adds a lint over every ADR rather than a PreToolUse hook, so the check covers human-authored ADRs too.

## Stack and toolchain (shipped assumption: TS/JS with pnpm, Python with uv)

- `CLAUDE.md` (shipped) — Python and Javascript/Typescript sections, pnpm/Turborepo guidance, Company Overview/`[project standards]`/Architecture/Deployment placeholders. → prune sections for absent stacks, add the real stack's conventions, resolve every placeholder; `implement-task` discovers validate commands from this file, so its accuracy is load-bearing.
- `docs/company/company-overview.md` — bracketed narrative skeleton (company, customers & users, product, project fit) that the shipped `CLAUDE.md` Company Overview section points at; descriptive only, no rules live in it. → fill the brackets with the user during init — they know the company, never invent content; a project with no company framing deletes the doc and rewrites the `CLAUDE.md` Company Overview section into a plain project overview.
- `scripts/setup/doctor.sh` — warn-only LSP binary checks gated on TS and Python manifests, shipped wired into `package.json` `prepare`; its comment block maps other languages to official plugins and binaries. → retarget the checks to the detected stack; on the copy path, wire into the destination's install lifecycle (`prepare`, or the stack's equivalent).
- `scripts/setup/check-install.mjs` — preinstall guard that hard-fails non-pnpm installs (reads `npm_config_user_agent`) and wrong Node majors; assumes a repo-root `.nvmrc` (resolved two levels up from the script's own location, shipped with the template's pin) and the shipped `package.json` `preinstall` wiring, passing silently when `devEngines.runtime` in `package.json` supplied a matching Node. → project-init retargets the pin in all four mirror sites together — `.nvmrc` (the exact version the guard reads), `engines.node` (the range it enforces, `>=X.Y.Z <X+1`), `devEngines.runtime.version` (the same exact version, what pnpm downloads), and `pnpm-lock.yaml` (regenerated by running `pnpm install` and committing the result, because pnpm turns `devEngines.runtime` into a `node: runtime:<version>` dependency and a stale lockfile fails every `--frozen-lockfile` install, which is CI's default) — and the guard itself now hard-fails on drift between the first three, so a partial retarget stops the install with the drifted field named rather than presenting as a broken machine; never pin the runtime through `pnpm-workspace.yaml`'s `useNodeVersion`, which pnpm 11 removed and now ignores without warning while `pnpm config get use-node-version` still echoes the value back; `devEngines.runtime.version` stays an exact version and never becomes a range, because a range breaks the pin on both pnpm lines: pnpm `<=10` abandons runtime resolution and installs the third-party `node` npm package (bin creation fails, blocked setup script, lifecycle scripts on the ambient Node), while pnpm 11 resolves a runtime but its build script trips the allowlist (`ERR_PNPM_IGNORED_BUILDS`) so `pnpm exec` fails at startup — both measured; the known cost of the exact spelling is accepted, that npm reads `devEngines` before `preinstall` and treats `onFail: "download"` as `error`, so `npm install` on any other Node dies with `EBADDEVENGINES` rather than reaching the pnpm-only message, which still stops the install and only degrades the diagnosis; a musl-based destination (Alpine images) provisions the pin like glibc ones — pnpm's runtime resolution serves musl variants from `unofficial-builds.nodejs.org`, community builds pinned by lockfile integrity rather than release-signed tarballs — and deleting the `devEngines` block to let the base image supply Node remains a supported opt-out the guard treats as deliberate; any diff touching the lockfile's `node@runtime:` block is reviewed by hand rather than waved through as generated, confirming every `url` host is `nodejs.org` (or `unofficial-builds.nodejs.org` for the musl variants) and every `integrity` matches that release's published checksums, since pnpm fetches those URLs verbatim from whatever host they name; a non-pnpm shop is a deliberate fork of the agent check, never a silent bypass; a destination that declines the guard deletes the file and the `preinstall` script together.
- `scripts/setup/check-install.mjs` engineStrict/devEngines gate — the guard hard-fails an `engineStrict: true` (in `pnpm-workspace.yaml` or `.npmrc`) alongside `devEngines.runtime` only when the running pnpm major is `<=10` or unparseable; that deadlock is a pnpm `<=10` behavior, and on pnpm 11+ the runtime is provisioned before the engines check so the pairing installs cleanly (measured) and the guard leaves it alone. → an instance on pnpm 11+ may keep `engineStrict: true` alongside `devEngines.runtime` to regain hard dependency-engine blocking without the deadlock; an instance on pnpm `<=10` keeps the two apart or upgrades pnpm; the shipped template sets `engineStrict` nowhere, and the guard's wrong-Node check is advisory on pnpm 11 because preinstall runs under the provisioned runtime.
- `package.json` + `pnpm-workspace.yaml` + `turbo.json` + `apps/`/`packages/` — the shipped repo shape: a `private: true` pnpm workspace root with a Turborepo task graph (`build`/`dev`/`lint`/`test`/`typecheck` routed through `turbo`), Prettier + husky pre-commit, and pnpm-only installs; `pnpm exec`/`pnpm dlx` are the convention and `npx` appears nowhere in the payload. → single-app destinations take the collapse offer (delete `apps/`/`packages/`/`turbo.json`, drop the workspace globs, de-turbo the scripts); every destination renames the `name` field; on the copy path an existing `package.json` merges rather than clobbers.
- `.claude/settings.json` `enabledPlugins` — `typescript-lsp` and `pyright-lsp` enabled. → enable the detected languages' LSP plugins, disable dead ones.

## MCP servers, plugins, and agents

- `.mcp.json` — ships `supabase-local` (an HTTP stanza at `http://127.0.0.1:54321/mcp` for a local Supabase dev instance; delete when the project runs no local Supabase, rename per the slug norm if kept), plus `playwright-local` (chromium) and `firefox-devtools`, both version-pinned and launched via `pnpm dlx` (the payload is npx-free), with `firefox-devtools` `START_URL` neutral at `about:blank`, plus boilerplate HTTP stanzas for commonly-used services — `clerk-[project]` (`https://mcp.clerk.com/mcp`), `cloudflare-[project]` (`https://mcp.cloudflare.com/mcp`), `stripe-[project]-[environment]` (`https://mcp.stripe.com`; a Stripe session binds to one account and one environment, live or a sandbox, hence the extra discriminator — one entry per account-environment pair), and `posthog-[project]` (`https://mcp.posthog.com/mcp?project_id=[id]`, URL-pinned because a PostHog session can otherwise switch orgs and projects at will) — named per the OAuth isolation norm below. The file is plain JSON: Claude Code does not discover `.mcp.jsonc`, and comments fail the parse and kill every server in the file (verified empirically against `claude mcp list`). → add the project's servers; remove the browser servers if the project has no UI to verify; point `START_URL` at the project's real dev URL once one exists; verify the boilerplate stanzas were curated at project creation — the user renames the keepers and deletes the rest by hand before this audit ever runs — and treat any still-placeholder stanza as an accident to flag: `enableAllProjectMcpServers` in shipped settings auto-approves every `.mcp.json` server, so a leftover placeholder connects silently instead of prompting anyone.
- **OAuth account isolation** (shipped assumption: no account-bound OAuth servers pre-configured) — Claude Code keys MCP OAuth tokens by server name in one machine-global store, so a fixed-name server (every plugin and user-level server) shares a single token across every project on the machine; the shipped `CLAUDE.md` MCP Tools section states the norm: account-bound OAuth servers land project-scoped in `.mcp.json`, named `<service-server>-<slug>`. → for each account-bound OAuth service detection finds (plugin or user-level — Cloudflare, Linear, Stripe, ...), ask whether the user holds one account everywhere or per-project accounts; one-account services stay on the shared fixed-name server, per-project services get the isolation package: project-scoped suffixed servers in `.mcp.json`, `deny` entries in `settings.json` for the shared variant's account-bound tools (only when that shared variant actually exists), no `permissions.allow` wildcards for the suffixed servers (account-bound writes prompt by design), and a destination `CLAUDE.md` bullet naming the servers, the account they are OAuth'd to, and the two never-rules from the shipped `CLAUDE.md` MCP Tools norm bullet, copied verbatim rather than paraphrased.
- **Project MCP slug** — the suffix's only job is uniqueness in the machine-global token store. → reuse the project's codified slug if `CLAUDE.md` already carries one; else derive a short distinctive slug (initials or a natural shortening, never the full repo name) and confirm cross-project uniqueness with the user — only they know their other checkouts; codify the confirmed slug in the destination `CLAUDE.md` MCP Tools section; one slug per project, reused across all its suffixed servers.
- **Cloudflare (worked instance)** — one unified HTTP server, shipped as the `cloudflare-[project]` boilerplate stanza in `.mcp.json` (`https://mcp.cloudflare.com/mcp`): its `docs`/`search`/`execute` tools wrap documentation search, the OpenAPI spec, and the full API surface (~2,500 endpoints via `cloudflare.request()`), replacing the older per-product server set (bindings, builds, observability). → rename with the project slug, or delete the stanza if the project has no Cloudflare; extend from Cloudflare's catalog only on demonstrated need (radar, browser-rendering, AI gateway); docs search stays on the plugin — it is unauthenticated, so the isolation rule does not apply; when a Cloudflare plugin is present at any level, deny its account-bound tools in project `settings.json` (`mcp__plugin_cloudflare_cloudflare-api__execute`, `mcp__plugin_cloudflare_cloudflare-bindings__*`, `mcp__plugin_cloudflare_cloudflare-builds__*`, `mcp__plugin_cloudflare_cloudflare-observability__*`).
- `.claude/settings.json` `enabledPlugins` — `chrome-devtools-mcp` enabled (kept for its skills; the project `.mcp.json` `chrome-devtools` entry shadows its server by name); Linear and Context7 are not plugins but project-scoped `.mcp.json` entries (`linear-[project]`, keyless `context7`). → match reality: disable unused plugins, and keep the tracker's `.mcp.json` stanza in step with the tracker actually in use.

Checklists in `review-board/references/` are stack-neutral best practice. → verify tool viability; add checklist content only on a clear project signal (e.g. a payments integration justifies a PCI note in security), proposed as its own plan item.

## Secrets protection (shipped assumption: env-file conventions — `.env*`, Cloudflare `.vars`)

- `.claude/settings.json` `permissions.deny` — the `Read(...)` entries are the single secret-file registry: enforced natively for file tools, `@file` references, and recognized shell readers, and parsed at runtime by `guard-secret-read` for everything else Bash can do. Example env files stay readable by omission from the enumerated env entries (`.env.example` matches none); vars example files stay readable through hyphen spellings (`.dev.vars-example`), because dot spellings (`.dev.vars.example`) match the `.*.vars.*` wildcard, which stays broad since wrangler env names are user-defined and the wildcard cannot be narrowed. → init's secret sweep (detection) plus classification (interview) appends the project's uncovered secret files (SOPS files, `serviceAccount*.json`, `*.tfvars`) as deny entries; a project whose example convention uses dot spellings renames those files to hyphen spellings rather than loosening the wildcard.
- `.claude/hooks/guard-secret-read.mjs` + its `PreToolUse` `Bash` entry in `settings.json` — token-matches Bash commands against the deny registry, any verb (relocation and `git add` count as leaks), with an inline `case` prefilter listing the registry's substrings; needs `node` on PATH like the sibling guards. → every appended deny entry lands with a matching prefilter token in the same edit — the hook body never needs per-project edits.
- `CLAUDE.md` (shipped) Standards — the secrets rule bullet: the block stated as fact, the inline-substitution hand-off protocol, the `!` output test, the same-change maintenance clause. → keep in lockstep with the registry and hook; a project that removes the hook removes the bullet's hook clause with it.

## Drift greps

Run over `.claude/skills`, `.claude/agents`, `.claude/settings.json`, `.claude/hooks`, `scripts/`, and the shipped `CLAUDE.md`; anything matching outside the entries above is drift — treat it as an unmanifested fork point and handle it like any other finding.

- Platform: `grep -rniE 'github|gitlab|\bgh\b|\bglab\b|pull_request|merge_request'`
- Tracker: `grep -rniE 'linear|jira|docs/tasks|docs/briefs|docs/designs|docs/initiatives|docs/assets'`
