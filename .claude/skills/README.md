# Agent Skills Overview

## The chain

One front door for interview sessions, five lenses behind it, and a task file that carries work from capture to done. Keystone principle, written into the skills verbatim: **ceremony scales with size; engineering discipline never does** — a one-line chore still gets grilled, built test-first, and validated; what collapses for small work is artifacts and process, never rigor. Three fixed stops on every implementation path. The **surface gate** — work that creates or reshapes a user-facing surface proceeds only with a `grill-design` outcome in hand (a design artifact or a stated governed-verdict), because composition is authored before code or composed from the API payload by accident. The **incumbent gate** — every scoped task states what happens to the existing implementation in its `incumbent:` key (`none`, `replace`, or `extend`), and a `replace` verdict runs the demolition pass before the first slice, because a build session holding the old code treats a design as a diff request against it and a missing verdict is not a quiet `extend`. And the **human QA gate** — the session hands the user instructions to see the change in action and waits for their verdict; nothing is marked done and neither `/review-board` nor `/stage-for-commit` gets recommended until the user has seen it work.

```
/grill-me (router; /grill-me @<artifact file> routes by the file's kind + status to the next step in its flow)
   ├─> grill-initiative ──> initiative doc (docs/initiatives/: verbose Direction + thin Portfolio rows) ─> hard stop
   │        ├─ pickup: /grill-me @<initiative> ─> next queued project, one at a time ─> grill-product (brief flow below)
   │        └─ reorientation close (direction contradicts standing docs): CLAUDE.md interim-marker offer + estate-reconciliation recommendation, both on the user's word
   ├─> grill-design ──> grammar check ─> design artifact (docs/designs/) or governed-verdict ─> hands into grill-engineer
   │      (the mandatory first stop for every settled surface-bearing ask; also compiles external-tool mockup prompts, the returned mockup re-entering as a supplied design)
   ├─> grill-engineer (≈8/10) ──┬─ build now ─> /tdd ─> human QA gate ─> /stage-for-commit (user commits)
   │      (chains back into grill-design when surface work arrives without its outcome; build-now states the incumbent verdict in-session, demolition pass when replace)
   │                            ├─ spec it ──> docs/tasks file (status: scoped, incumbent: verdict, design: artifact link)
   │                            │                 └─> /implement-task ─> demolition pass when incumbent: replace (agent deletes; type errors = connection map)
   │                            │                        └─> slice loop (/tdd, first-render check, commit per slice; connection map shrinks to zero)
   │                            │                               └─> task-end render pass ─> human QA gate ─> /review-board offer ─> /ship-pr offer ─> stop
   │                            └─ park it ──> /capture-task
   ├─> grill-product ──> design docs / ADRs / capture / nothing — hands up to grill-initiative when workstreams decompose into project-shaped units
   │        └─ product brief (docs/briefs/, status: draft; initiative: back-link when portfolio-spawned)
   │              ├─ single workstream ─> seeds grill-design (surface-bearing) or grill-engineer (feasibility + spec against the code)
   │              └─ multi-workstream ─> /ground-brief (same session) ─> status: grounded ─> fresh session per workstream, in recommended order
   └─> grill-research ─> summary writeup / capture / nothing

/capture-task — park anything, any time; the captured file seeds a later grill-engineer session
/diagnose — the bug front door: feedback loop → repro+minimize → ranked hypotheses → fix via /tdd + human QA gate; no-seam and prevention findings → /capture-task
/curate-context — the gate on prescriptive context files (CLAUDE.md, README.md, design docs): loaded on every edit by the skill description and the CLAUDE.md rule, distillation of a session's lessons is one entry path; vocabulary, shape facts, and ADRs hand off to domain-modeling
/ship-pr — the work chain's one door to the remote: push the branch and open a PR documenting QA and the review-board outcome; offered by implement-task and review-board, run only on the user's word
primitives under the hood: grilling, domain-modeling, tdd, skill-creator
```

The task file lifecycle lives in its frontmatter: `captured` (filed, unknowns explicit as `TBD (needs grilling)`) → `scoped` (grilled; design decisions, test strategy, and slices written) → `in-progress` → `done`. The shared format is defined once in `capture-task/assets/task-template.md` and referenced by capture-task, grill-engineer, and implement-task; every scoped task states its `incumbent:` verdict, and a surface-bearing task additionally links its grill-design artifact via `design:` frontmatter. The artifact tiers mirror Linear's hierarchy — initiative (`docs/initiatives/`, direction grouping projects) → brief (`docs/briefs/`, the project document) → task (`docs/tasks/`, the unit of work) — chained upward by `initiative:` and `brief:` frontmatter, with raw source material (notes, transcripts, examples, stored design sources) living verbatim under `docs/assets/<slug>/`, classified before storage; lower tiers exist happily without upper ones, and most work enters as a one-off brief or task. No GitHub issues anywhere in the chain — the file is the tracker; push and PR happen only through `/ship-pr`, only on the user's word. The single carve-out sits outside the chain entirely: `/template-feedback` files issues against the **template** repo, reporting defects in the tooling rather than tracking this project's work, so the file remains the tracker for everything the chain builds.

## project-init

One-shot onboarding auditor, run once right after this template lands in a destination project — a fresh instance from GitHub's "Use this template" (single squashed commit, unrelated history) or the payload copied by hand into an existing repo — and never again: detects the git platform, CI, stack, tracker, MCP surface, and secret-candidate files not yet covered by the `Read(...)` deny registry — including git archaeology, live only on the copy path, to recover a clobbered pre-existing partial suite as interview talking points — then interviews the user via `grilling` as an onboarding auditor on everything a repo cannot answer (tracker shape, secret-file classification, compliance posture, team composition, single-app versus monorepo, and a missing whole-program typechecker — an agenda item rather than a recorded fact, since the demolition pass reads the compiler's error set as its connection map, branched on adoption cost), and applies an itemized, individually approved tailoring plan across skills, agents, `settings.json`, hooks, scripts, and the whole `CLAUDE.md` — including clearing template residue (the template's own `docs/` artifacts, `CONTEXT.md`/`ARCHITECTURE.md`, `.claude/rules/template-dev.md`), stamping the template lineage into `CLAUDE.md` from `CHANGELOG.md` before deleting the local copy, rewriting `README.md` into the project's own (carrying the template-updates recipe), renaming `package.json`, and offering the monorepo collapse for single-app destinations. Validates the suite's 8-of-10 best-practice assumptions against this project and hunts the 2-of-10 misfits; facts land in `CLAUDE.md`, in-place skill edits are reserved for genuine behavioral forks mapped in `project-init/references/fork-points.md`. Strictly user-invoked, and its final approved plan item is deleting itself — this section included, with `sync-template` explicitly surviving as the long-lived update channel; later drift (a tracker adopted mid-project, a platform migration) is normal work for `grilling` and `curate-context`, not a re-init.

## brand-init

The brand-derivation ceremony and sole owner of filling `BRAND_DESIGN.md`: runs `grilling` with `domain-modeling` active, framed as a brand partner, opening on the mood-board gate — image files in `docs/branding/moodboard/` are distilled through the interview (per image: what draws the user → extracted attributes, never a layout or palette wholesale) into foundations, identity tokens, anchored steering sections, four-part voice, and anti-goals harvested from the session's own rejections; a missing or empty board gets one confirm, stop-and-curate (curation guidance handed over: Dribbble for mood, shipped products for anchors, mood altitude not screenshots) or continue with anchor interrogation as the differently-curated alternative. `references/brand-research.md` carries the locked evidence base and the deliberate structural decisions so no future session re-runs the research or re-litigates the doc's two-tier grammar. `grill-design` refuses inline brand derivation and signposts here; user-invoked, never auto-chained, re-runnable as a brand refresh (a contradiction with the filled doc halts for the user's pick, per `curate-context`); exits by writing the filled doc through `/curate-context`.

## sync-template

The pull-based update channel between an instance and the template it came from: reads the `Template lineage:` stamp in `CLAUDE.md`, fetches the template remote (tags namespaced so they never collide with the project's own), and walks every template `CHANGELOG.md` release newer than the stamp as an itemized adaptation interview — apply clean, adapt to this project's posture (compliance rules, tracker, collapsed monorepo, deliberately forked skills; the release's adaptation notes seed the negotiation), or reject with a recorded reason in `docs/template-sync-log.md` so no release gets re-litigated. Lands working-tree changes only — the user commits through the project's own flow — then updates the lineage stamp. Strictly user-invoked and strictly child-side: the template never pushes into instances, and the skill refuses to run in the template repo itself. A missing stamp on a real instance triggers first-run onboarding (confirm the template repo, add the remote, establish the baseline version with the user) instead of a failure. The release diff is pathspec-scoped to exclude the template's own residue — `CHANGELOG.md`, `.claude/rules/template-dev.md`, `.claude/skills/project-init/`, and the template's `docs/` working artifacts plus `CONTEXT.md`/`ARCHITECTURE.md`/`CONTEXT-MAP.md` — mirroring the set `project-init` clears, so a release never offers an instance the parent's task files, decision records, or the init skill that deleted itself; `docs/company/` is excluded from that exclusion, being payload skeleton that stays.

## template-feedback

The child-to-parent reporting channel, paired with `sync-template`'s parent-to-child one: run from an instance, it turns the caller's complaint plus the session that produced it into a scrubbed GitHub issue against the template repo, or declines and says why. Strictly user-invoked via `disable-model-invocation: true` rather than a worded trigger — the caller is the detector, because a session appraising its own output for signs of user frustration either never fires or fires as deflection, filing template debt for its own bad reasoning. Validation runs lookup-heavy with two questions as the ceiling: a lineage check (already fixed in a release newer than the `CLAUDE.md` stamp → no issue, run `/sync-template`, the most common outcome), a sync-log check (an already-recorded rejection makes it a known misfit), and a local-fork check (a misfire inside an adapted artifact is disclosed or ruled out), then the session trace weighted by what the caller asked it to look into. Five verdicts — `defect`, `gap`, `misfit`, `upstream`, `not-the-template` — where reaching the last two is the actual work, since friction feels like a defect in the moment, and `misfit` is the highest-value output because it grows `fork-points.md` from evidence rather than speculation. The evidence gate is the one thing that does not yield to the caller (no narratable trace, no issue — and the refusal names what to capture next time), while the verdict stays an overridable recommendation. The trace narrates purely in template vocabulary, which is simultaneously the most actionable form for a context-free receiving session and an already-scrubbed one for a public repo; a trace that cannot be told that way is itself the `not-the-template` finding. Files behind one non-skippable confirm showing the exact rendered body, after a duplicate search, with `from-instance` plus a kind label as the join key for the aggregate view. Refuses in the template repo itself.

## grill-me

User-invoked router (never model-triggered) and the one front door for grilling sessions: parses an explicit lens argument (`/grill-me engineer: <ask>`), a bare lens, a freeform ask whose lens it infers, or an artifact file reference, then hands off to `grill-initiative`, `grill-engineer`, `grill-product`, `grill-design`, or `grill-research`. The lens skill declares itself in its opening line, so a wrong inference costs one corrective sentence. File-seeded routing makes `/grill-me @<artifact>` the universal continue button: the router reads the file — taxonomy home for altitude, frontmatter for lifecycle position — and infers the next step in that artifact's flow (an active initiative picks up its next queued project, a draft multi-workstream brief runs `ground-brief`, a captured task gets scoped, a scoped task offers `implement-task`), stating the inference in one line before proceeding. Direction-scale language (reorientation, re-baseline, organizing many features into projects) routes to `grill-initiative` directly, and a missed initiative route costs nothing because `grill-product`'s scale detection hands up mid-session. Settledness of the _what_ is the first routing check: a fuzzy or fanning-out ask leads with `grill-product` even when phrased in engineering vocabulary — mis-routing to product is nearly free (the hand-off carries into `grill-engineer` once the what proves settled) while mis-routing a half-baked idea to engineer designs the how of an undecided what. The second check is surface-shaped: a settled ask that creates or reshapes something user-facing routes through `grill-design` first (its grammar check fast-exits into `grill-engineer` when the docs already govern the surface), and engineer stays the default only among settled, surface-free asks. Routes once and gets out of the way.

## grilling

Relentless one-question-at-a-time interview that walks the decision tree of a plan, request, or captured task until shared understanding is reached: biggest decisions first, a recommendation with reasoning attached to every question, facts looked up in the codebase while decisions stay with the user. Opens by naming subject and objective, stops when the objective is met, and leaves nothing behind beyond the shared understanding in conversation. Model-invocable on 'grill' trigger phrases or whenever a plan needs stress-testing before implementation. The lens skills run it under their own frames; an ask that fits an engineering, product, design, initiative, or research lens loads that lens skill instead of this bare primitive.

## grill-engineer

The engineering lens (roughly 8 of 10 sessions): runs `grilling` with `domain-modeling` active, framed as an implementing-engineer peer with the codebase as ground truth for what exists and Context7 (falling back to web search → web fetch) as ground truth for how the stack's libraries actually behave. At objective-met it asks one exit question with a size-based recommendation — build now (`/tdd`, validate, human QA gate, then `/stage-for-commit`), spec it (evolve or create the docs/tasks file with design decisions, test strategy, and vertical tracer-bullet slices, flipping `status: scoped`), or park it (`/capture-task`) — and pure discussions simply end with no forced exit. Spec-it owns the full authoring depth — deep dive, design decisions, slicing — with `references/example-scoped-task.md` as the worked example of a scoped file's shape and altitude. A product brief from `docs/briefs/` can seed the session the same way a captured task can — a grounded multi-workstream brief seeds one workstream at a time, with spec-it copying that workstream's contracts into the task file and recording the `brief:` back-link — and mid-grill fan-out (independently shippable outcomes multiplying while the what stays unsettled) is a named hand-up trigger to `grill-product`, since this lens's exits are all singular. Spec-it binds a surface task's acceptance criteria by name to the design artifact's Experience intent and Source fidelity sections — criteria, not background context, and bound rather than transcribed so a mid-build artifact amendment cannot strand the task on a stale copy. Surface work carries its own gate: a task that creates or reshapes a user-facing surface enters only with a `grill-design` outcome (design artifact in `design:` frontmatter or a recorded governed-verdict), and finding neither the session chains into `grill-design` before any engineering. Spec-it also sets `incumbent:` on every task — `none`, `replace`, or `extend` — the call that decides whether `implement-task` demolishes the existing implementation before building; the key names the mechanism rather than the genre of work, this exit is the one place every path makes it, and the build-now path states the same verdict out loud since no task file carries it there, running the same demolition pass when it lands on `replace`.

## grill-initiative

The direction lens, one tier above `grill-product`, modeled on Linear's hierarchy (initiatives group projects toward a goal; projects — briefs here — group issues — task files — toward a deliverable): runs `grilling` with `domain-modeling` active, framed as a product-strategy partner distilling a multi-project ask — a whole-product reorientation, a new strategic direction, or a large sweep of unbuilt features arriving in one conversation — into one initiative document at `docs/initiatives/YYYY-MM-DD-<slug>.md` (shaped by `references/example-initiative.md`). The document carries two deliberately opposite registers: a verbose `## Direction` section — the constitution downstream sessions inherit, with rejected alternatives, cross-cutting doctrine (product constraints only — the delivery machinery of artifact types, homes, and owning skills stays the skills' own), and every decision's why, because at direction scale the residue is the deliverable — and a `## Portfolio` of thin project rows in pickup order (status `queued` | `in progress` | `done` | `dropped`, plus outcome, dependencies, done-when; `done` judged manually, `dropped` rows kept with their why). Raw source material stores verbatim under `docs/assets/<slug>/`, classified before storage. No eager children: portfolio rows are the only per-project artifact at initiative time — briefs and tasks are written at pickup, one project at a time via `/grill-me @<initiative>`. Closes with a hard stop like `ground-brief`; when the direction contradicts standing docs, the close also offers the `CLAUDE.md` interim marker (via `curate-context`) and recommends the estate-reconciliation sweep — classify every standing ADR/task/brief/design against the Direction as obsolete/amend/unaffected — run only on the user's word. Entered by explicit direction-scale asks via `grill-me` or by `grill-product`'s scale hand-up; most product work is a one-off brief, and the lens never manufactures an initiative for a lone feature.

## grill-product

The product/design lens: runs `grilling` with `domain-modeling` active, framed as a product-design partner grounded in `UI_UX.md`, `BRAND_DESIGN.md`, the existing UI code, and web research into named design patterns, accessibility standards, and published UX findings — recommendations come from real-world evidence, never invented UI/UX concepts, and stay at design altitude (what and why, never how). Web-evidence questions dispatch the `research-analyst` agent (`.claude/agents/research-analyst.md`) in the background so the interview continues in real time while sourced claims arrive. Exits offer only what crystallised: design-doc updates, a product brief in `docs/briefs/` (shaped by `references/example-product-brief.md`, evidence-grounded and implementation-free, written with `status: draft` frontmatter, and stating plainly in Position when it replaces something already shipping, since a brief silent on the old thing's fate gets read against the existing code downstream), an ADR, a captured task, or nothing at all. Mid-session fan-out detection catches fog-plus-fan-out — two or more independently shippable outcomes while the what stays unsettled — with a one-line naming confirm, after which the interview consolidates the feature-set: workstreams split on UI/UX seams with restraint, each entry carrying its own settledness call (settled ones captured and linked on the spot). Session boundaries follow the residue principle: a single-workstream brief seeds the next lens and continues in-session by default (`grill-design` first when the workstream carries a user-facing surface, then `grill-engineer`); a multi-workstream brief chains into `ground-brief` in the same session, then stops hard — every workstream grilling runs fresh from the grounded brief. Fan-out has a ceiling: when workstream candidates keep decomposing into project-shaped units — each needing its own product session — scale detection names initiative scale in one line and, on the user's nod, hands up into `grill-initiative` in-session, residue intact.

## grill-design

The composition lens between product and engineering: runs `grilling` with `domain-modeling` active, framed as a design partner at composition altitude — what a user-facing surface looks like (decision job, experience intent, hierarchy, per-breakpoint layout, control choices, disclosure plan), never how it is built. Every session opens with the grammar check against `UI_UX.md`: a governed surface exits in minutes with a stated verdict straight into `grill-engineer`; an ungoverned or strained one (a new interaction model on a familiar container counts) runs the full composition interview and writes a design artifact to `docs/designs/YYYY-MM-DD-<slug>.md` (shaped by `references/example-design-artifact.md`), which the task file links via `design:` frontmatter and `implement-task` builds to. Both hand-off exits additionally state whether the composition replaces the incumbent surface or extends it when the surface already ships — the judgment is cheapest in the session holding new against old, while `grill-engineer` remains the single writer of `incumbent:`. Every artifact carries falsifiable Experience intent assertions the build's render checks judge feel against; a supplied design (mock, wireframe, reference) additionally runs the fidelity contract — the source classified before storage (real customer or production data never lands unredacted) and stored under `docs/assets/<artifact-slug>/` recorded in `source:` frontmatter, its working qualities transcribed into a Source fidelity inventory before any doc validation (never by reference to the incumbent surface on reshapes), intent derived from the source, every doc-conflict cut weighed against the inventory out loud, and the cumulative composition re-examined against the source once before adoption. The default-on rule exists because judgment-gated design passes demonstrably undertrigger — every settled surface-bearing ask routes through here, and the skip is a stated, auditable verdict rather than a silent decision. The mockup path is the outbound half of Supplied: from a grilled position (a brief in hand, or this session's own settled interview — never an ungrilled idea), the session compiles one prompt per surface for an external AI design tool — the feature's cold hard facts plus distilled brand non-negotiables, never pasted doc contents — and the validated mockup the user brings back re-enters through the fidelity contract. Web-evidence questions dispatch the `research-analyst` agent in the background. An unsettled what surfacing mid-interview hands up to `grill-product`, mirroring the other lenses' hand-ups. Skeletal design docs stop the session with a one-line signpost to `brand-init` — brand derivation is its own ceremony, never an inline side effect; a genuinely new grammar earns a one-time `/curate-context` offer into `UI_UX.md` — the flywheel that makes future surfaces arrive governed.

## ground-brief

The engineering reconciliation pass between a product-pure multi-workstream brief and the isolated workstream grillings it seeds: reads the brief and the code each workstream would touch at orientation depth, then produces per-workstream feasibility (with the risky bit named), cross-workstream contracts (interface-level promises that keep later workstreams grillable and buildable in isolation), and a recommended grilling order. When the code contradicts the product split, it surfaces a re-split proposal as a user decision with costs attached — never redrawing product lines silently. One HITL approval gates the write: it appends the brief's `## Engineering grounding` section, applies accepted re-splits to Workstreams, and flips `status: draft → grounded` — the one brief fact not derivable from child task files. Chained in-session from grill-product's brief exit (judging re-splits needs the interview residue) or invoked standalone on a draft brief; declines single-workstream briefs, which seed their feasibility session through the router (`grill-design` first when surface-bearing, else `grill-engineer`). Closes with a hard stop and pickup instructions: each workstream is grilled in a fresh session, one at a time, in the recommended order — the grounded brief carries everything a cold session needs, which is the point of the pass.

## grill-research

The research lens: runs `grilling` framed as a research analyst, facts sourced via Context7 → web search → primary docs, with no build pressure by construction — it never steers toward implementing in this codebase. Anything past a quick Context7 pull dispatches the `research-analyst` agent (`.claude/agents/research-analyst.md`) in the background — announced in one line, results woven in when they land — so the interview never stalls on a fetch. Exits: a summary writeup (suggest `docs/notes/`), a captured task if an actionable idea emerged, or nothing, which is the normal case and counts as success.

## implement-task

The fresh-session resume door: reads a `scoped` task file from `docs/tasks/`, refuses to build on main or on under-specified files (those get routed back to a grilling first — including a surface-bearing task with neither a `design:` artifact nor a governed-verdict, which routes back to `/grill-design`, and a task carrying no `incumbent:` key, since a missing verdict is not a quiet `extend` and the build session never writes the key itself), runs a doc pre-flight before the tree splits — uncommitted docs and context files lingering from earlier sessions get one offer to stage them with a ready-to-paste commit message, so the user can commit on `main` and the new branch inherits them — then moves the session into a dedicated worktree (`scripts/setup/gwt-add.sh --no-open` + `EnterWorktree`, one confirm; declining falls back to a plain feature branch in the checkout), runs the demolition pass first on an `incumbent: replace` task — carve-outs screenshotted and stored before anything goes, then the write-capable `demolition` agent deletes the incumbent and its tests in its own context window so the build session never reads them, returning a forward-requirement record and a compiler error set that becomes the build's connection map (each slice shrinks it, zero before the QA gate, so a green project typecheck is not the per-slice bar while it is open) — then builds slice by slice — deep plan (UI slices read the design artifact as the composition contract; deviation is a surfaced decision, never a silent redesign), `/tdd`, validate (typecheck and single test files regularly; never the full suite mid-task; the slice that first renders a new surface adds a screenshot render check at both breakpoints judged against the artifact — its Experience intent included — and diffed against the stored source design when `source:` names one, with the comparison scoped to the qualities the fidelity inventory names, never palette or theme, and drift verdicts citing the violated line; the judging sections are the build's contract, never edited to fit a failing render), commit per slice with the task file's checkboxes riding along — flipping status `scoped → in-progress → done`. DONE and DONE_WITH_CONCERNS continue automatically; only BLOCKED stops. Runs the full test suite once at the very end, then a task-end render pass over every touched surface (both breakpoints, both themes, same three-reference judgment, screenshots carried into the QA handoff, which leads with the source-versus-build comparison when a stored source exists), then stops at the human QA gate — a QA script the user runs to see the change in action, with nothing marked `done` until they confirm — then offers `/review-board` (recommending yes for anything non-trivial) and stops before any push or PR.

## tdd

Test-driven development discipline: red before green, one seam at a time, tests only at pre-agreed public seams, each cycle running a dependency-bounded neighborhood (the seam's tests plus its direct consumers, lint on touched files only) with the full suite once at the end, with the anti-pattern catalog (implementation-coupled, tautological, horizontal slicing) in sibling reference files. Carries the UI seam split: layout, appearance, and composition are never test targets (jsdom computes no layout, so tests are design-blind) — view logic and behavioral contracts get the full discipline while appearance belongs to the design artifact and render checks, and appearance-shaped tests found in touched test files are cleaned up in the same change, re-expressed at a behavior seam where they smuggle a real guarantee. Invoked under the hood by grill-engineer's build-now exit and implement-task's slice loop; also triggers directly whenever a feature or bug fix a test can lock down is being implemented, even when nobody says test-first.

## skill-creator

The skill-authoring primitive and the mandated path for any change under `.claude/skills/`: a CLAUDE.md rule plus wire-ins in grill-engineer's build-now exit and implement-task's deep plan load it, and the `guard-skill-edit` PreToolUse hook denies skill-file edits until it is loaded. Carries the authoring discipline — trigger-accurate third-person descriptions, progressive disclosure with references one hop deep, why-over-MUSTs style, rewrite-accreted-prose — with limits, frontmatter keys, and sources in `skill-creator/references/skill-quality.md`, and closes every substantive change with a gut-check handoff: test prompts the user runs in a fresh session, because the authoring session is too warm to prove cold-start triggering. Every change lands with its checklist: README blurb updates and fork-points coupling checks. It never runs tests itself — evaluation is the user's fresh session, not the author's warm one.

## review-board

Multi-agent review: spawns parallel specialist reviewers, each a registered agent in `.claude/agents/review-*.md` with its own checklist in `review-board/references/`, over the branch diff vs the detected default branch plus uncommitted changes (args can scope to a PR number, commit range, or paths). Two seat sets, chosen by what the change touches. Code changes get five (correctness, security, reliability, maintainability, performance/operations). A change whose subject is a documented process — runbook, contribution guide, agent or prompt file, API doc chain, ADR set, config that documents behavior — gets three instead (flow continuity, coherence, adversarial), because there the document is the behavior and nothing compiles it: flow traces producer-versus-consumer across the chain and hunts dead ends and gate bypasses, coherence hunts contradictions and stale counts in the files the change did not touch, and adversarial red-teams the null action and prices each available option against a reader taking the cheapest compliant path. The doc board never consolidates below three — the methods are traversal, agreement, and exploitation, and each finds what the others cannot — and its read depth inverts, defaulting to full changed-file reads because a prose diff loses the section that gives it meaning. A mixed change seats from both sets. An optional leading mode argument scales the board by shifting each seat's model tier rather than flattening to one model: `quality` runs full-file reads with Opus everywhere except maintainability on Sonnet (top tier buys nothing on checklist-shaped review), `balanced` tiers seats Opus (correctness/security — misses cost most, findings need intent/threat modeling), Sonnet (reliability/performance), Haiku (maintainability) with diff-first reads that escalate to full files per seat only on named triggers (unauthored code, cross-module contracts, security surface, tangled diff, concurrency), and `speed` runs diff-first with Sonnet on correctness/security (their misses are the point of even a quick pass) and Haiku on the remaining code seats. Those tiers describe the code board only; the documentation board keeps its own matrix, where adversarial and flow never drop below Sonnet and coherence covers from Haiku up. With no mode given the session AI never silently defaults: gate 1 opens with two recommendations — mode and depth posture — each reasoned from what it implemented this session and its own likely blind spots, then gate 2 confirms board composition; an explicit mode argument is respected as given, with at most a one-time reconsider case voiced at gate 2. The chair always runs on the session model, and seat-skipping (only when a code category has no surface in the change) applies in every mode; the three documentation seats are exempt and all three run whenever that board sits, since "this document has no gate to red-team" is an argument available against almost any document and it retires the highest-yield seat first. Small self-contained diffs can use a lite three-seat board in `balanced`. The session AI then acts as chair: dedupes findings, judges each from its own context (deep verification is deferred to the findings the human actually selects), renders a confirmed/plausible/rejected verdict with reasoning, and presents a consolidated report per `review-board/references/output-format.md` — decision-first, so every finding wanting the human's call is stated in plain language and ends in a question with the chair's recommendation attached, evidence is appended below the fold, and findings needing no decision shrink to one line each. Dispositions follow a finding's provenance rather than the size of its fix: anything the reviewed work introduced or worsened is fixed in the same session, and `/capture-task` is reserved for a pre-existing bug needing investigation the change has no grounds to run or a design tradeoff deserving its own decision, named as which. After the human gate resolves on a branch other than the default, the chair leaves an always-empty `review:` record commit — mode, verdicts, addressed and dismissed findings with the user's one-line reasons — pinning the board's outcome to the exact tree it reviewed, which is what `/ship-pr` later reads; it closes with a one-line `/ship-pr` offer when a remote exists.

Strictly human-in-the-loop: the report ends with "which findings should I address?" and nothing is fixed until the user picks. Invoke for pre-PR/pre-merge reviews, security passes, or any "review my changes" request.

## capture-task

Quick-captures a unit of work (bug, feature idea, or chore) as a structured task file at `docs/tasks/YYYY-MM-DD-<type>-<slug>.md`, built from `capture-task/assets/task-template.md` with every unknown kept explicit as `TBD (needs grilling)` rather than invented. No interviewing: it mines the current conversation for context (error text, file paths, decisions already made) so a fresh session can pick the task up cold with `/grill-me engineer:` or `/grill-engineer`. Captures always start at `status: captured` and omit the template's scoped-work sections — those arrive when grill-engineer scopes the task.

Suggest it once when the user voices an actionable aside, reports something broken they want parked rather than fixed now (fixing now is `/diagnose`), or drifts into "we should do X later" territory. Never auto-file; if the user doesn't bite, drop it.

## diagnose

The bug front door for anything broken the user wants understood or fixed now: a phased diagnosis discipline for hard or complicated bugs — build a red-capable feedback loop before any theorizing (the phase that _is_ the skill; no red-capable command, no hypotheses), reproduce and minimize until every element of the repro is load-bearing, test 3–5 ranked falsifiable hypotheses with one-variable probes, then land the fix through the chain: regression test via `/tdd` at a correct seam, human QA gate, a `/review-board` recommendation when the fix outgrew quick-fix size, and the usual commit exits — on a deliberately chosen non-main branch where the team flow requires one. Two findings are first-class rather than failures: "no correct seam exists" (the architecture prevents locking the bug down — documented and handed to `/capture-task`) and "cannot build a loop" (stop and ask for an artifact or environment rather than guessing). Post-fix, architectural prevention gaps go to `/capture-task` and a durable debugging gotcha earns one `/curate-context` nudge. Skip phases only when explicitly justified; a symptom is not a root cause.

Invoke on "diagnose", "debug this", "root-cause this", or any broken/failing/slow report the user wants investigated now — parking it for later stays `/capture-task`.

## stage-for-commit

Stages exactly the files changed during the current session by explicit path (never `git add -A`) and hands back a ready-to-paste commit message, then stops: no commit, no branch, no push, no AI attribution — the user is the committer. Proves the staged set with `git diff --cached --stat` before writing the message, and is concurrent-session aware: files another session already staged stay in the index and get flagged in the handoff (a `git commit` takes the whole index), and same-file collisions with unrecognized hunks are surfaced for the user to decide instead of silently staged.

Invoke at the end of a quick chore/feature/bug when the user wants to commit the work themselves — "stage my changes", "ready to commit", "write me a commit message for this". Also the landing step for grill-engineer's build-now exit, but only after the user's human-QA confirmation — never auto-chained straight from an implementation.

## ship-pr

The PR landing for branch-based work, and the chain's only door to the remote: pushes the current non-main branch and opens a GitHub PR whose body documents how the work was produced — Summary, QA evidence, and a Review board section reporting findings by verdict, what was addressed (with fix commits), and what was dismissed with the user's recorded reasons; "Not run." is a valid, self-indicting entry. Structure comes from `.github/PULL_REQUEST_TEMPLATE.md` (scaffolded on first use if missing, shipped in the template payload); review data comes from the `review:` record commit on the branch, falling back to session context, then to "Not run." Hard stops are mechanical only — on the default branch, no remote, dirty tree; process gaps (no review, unverified QA) get one nudge and then the truth in the PR body, because a skill that blocks on process gets routed around and the paper trail is lost exactly when it mattered. No AI attribution on the PR — the user is the author of record.

Strictly user-invoked and conditional by invocation, not configuration: solo projects committing to main simply never touch it, and no skill ever runs it automatically — implement-task and review-board close with a one-line offer at most. One confirm (exact title and body shown) before anything touches the remote; `draft` as an argument opens a draft PR.

## domain-modeling

Builds and sharpens the project's domain model as design happens: challenges terms against the `CONTEXT.md` glossary, sharpens fuzzy language, stress-tests relationships with concrete scenarios, cross-references claims with code, surfaces an ask's conflict with a documented boundary or invariant as a user decision with its cost attached rather than a silent constraint, and updates `CONTEXT.md` inline the moment a term resolves. Owns all three context-doc kinds — `CONTEXT.md` (language), `docs/adr/` (decisions), and `ARCHITECTURE.md` (engineering shape: a root topology doc plus per-context shape docs, created lazily and grown one true shape-fact at a time, never a stub, with an on-demand survey bootstrap when the user wants the whole map in one pass; format, growth, and maintenance contract in `domain-modeling/ARCHITECTURE-FORMAT.md`). Offers ADRs sparingly — only for decisions that are hard to reverse, surprising without context, and real trade-offs — and retires what each new one replaces in the same change: every ADR declares a `status` (`proposed` | `accepted` | `amended` | `superseded` | `deprecated`), a new decision greps its area and names what it changes via `supersedes` (retired whole) or `amends` (partly still binding), and the retired ADR gets the reciprocal field plus a note saying which clause died. Partial retirement is the common case, so `amends` is the default reach. Both the linkage and the ownership of the three doc kinds are stated rather than enforced, resting on this skill's description, its `ADR-FORMAT.md`, and the `CLAUDE.md` context-edit rule. Noticing what to declare stays the skill's job, and an ambiguous grep hit goes to the user rather than a guess. Active inside grill-engineer and grill-product sessions and directly on "document the architecture" asks; shape updates otherwise land with the code that changes the shape (implement-task's end-of-task shape check; review-board's correctness seat treats a contradicting diff as a finding).

## curate-context

The curation discipline for the prescriptive context files — every `CLAUDE.md` and `CLAUDE.local.md` (root, nested per-package, and the user-global `~/.claude/CLAUDE.md`), every `README.md`, path-scoped rule files under `.claude/rules/`, and `BRAND_DESIGN.md` / `UI_UX.md` — loaded on every edit to one of them, whatever brought it (design docs also accept a loaded grill lens; `.claude/skills/` stays `skill-creator`'s), with the descriptive docs (`CONTEXT.md` / `ARCHITECTURE.md` / `docs/adr/`) going to `domain-modeling` instead, holding the descriptive/imperative seam from both sides. No hook backs this: the skill descriptions and the `CLAUDE.md` context-edit rule are the whole mechanism, which is why both name the file paths explicitly. Ceremony scales with the edit while discipline never does. New rules run the full pipeline: friction attribution (prompt-steering A / undocumented convention B / model error C — only the (B)s survive), an admission bar that rejects anything already enforced by config, already documented in any skill or tool description a future session can read, subsumed by a general rule, or generic; routing to the narrowest correct file (imperative rules for the AI to the nearest enclosing `CLAUDE.md`, procedures a human performs to the nearest `README.md` — the test is who executes it — brand and UX foundations to the design docs, layout discovered at runtime since template and spawned projects differ); drafting; then a net-line-growth judgment on the edit as a whole, zero growth being the benchmark. Corrections verify against the code and land lean; deletions are surfaced, never silent. HITL is precise — no model-invented content lands unseen: model-proposed candidates need per-candidate approval, user-directed edits apply on the ask after the bar's pushback. The apply step is append-only and is the documented point-of-use exception to the CLAUDE.md prose restatement rule (its routing wins during an apply): near-duplicates strengthen the existing bullet, a contradiction halts for the user to pick the surviving statement, and a decayed target file gets flagged as a restatement candidate instead of receiving another append. "Nothing worth writing" is a valid and common outcome.

Distillation — "codify", "capture this convention", "add this to CLAUDE.md" — is one entry path, suggested at most once when a genuine candidate surfaces and never as a session-end ritual; the hook-gated edit path is the common one and fires whether or not anyone said the word.
