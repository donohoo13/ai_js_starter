# Add a demolition pass so briefs and designs outrank incumbent code

## Context

Instance sessions repeatedly report the same failure: a brief and a design artifact specify a new direction for an existing feature or surface in detail, and the implementation still lands on the original implementation with small tweaks. The bias is measured, not anecdotal. "To Add Is Machine, To Delete Is Human" (arXiv:2607.28887) defines deletion avoidance as the systematic tendency to retain code an intended edit requires removing, and finds across five frontier models on 197 SWE-bench Verified tasks that models locate the correct file over 92% of the time while removing the exact required line only 44.6-51.6% of the time; 29.0% of passing patches used a Guard-and-Go pattern (wrapping old code in a conditional instead of deleting it) and 61.1% of those patches were larger than the human developer's own fix. "Coding Agents Don't Know When to Act" (arXiv:2605.07769) found the mirror bias and, critically for this design, found that an explicit procedural instruction raised correct abstention from roughly 40% to 80.5-88.5% where stated preference did not. The suite already names this force twice, both times at design time only: `grill-design/SKILL.md:9` on payload gravity at build time, and `grill-design/SKILL.md:32` on the incumbent's curation being the strongest gravity in context. Nothing carries either belief into the build. Grilled in-session 2026-08-05 with research-analyst evidence; every decision below is user-confirmed.

## Problem

Current behavior: no artifact in the suite ever records whether work replaces an existing implementation or extends it, so `implement-task` reads the incumbent code as the strongest signal in context and treats the design as a diff request against it. `implement-task/SKILL.md:49` guards a build that _deviates_ from the design artifact, but keeping the old component and adjusting it never registers as a deviation, so preservation is unmodeled as a failure mode. Every destructive rule in the suite is post-hoc cleanup scoped to blast radius (`CLAUDE.md:46` orphan removal, `implement-task/SKILL.md:53` completeness audit, `tdd/SKILL.md:39` appearance-test cleanup), and the vertical-slice contract — each slice thin, compiling, demoable, and separately committed — leaves no legal place for a destructive step even for a session that wants one. Desired behavior: the artifact chain records a replacement verdict, `implement-task` refuses to build a task that never made the call, and a replace verdict runs a purpose-built demolition agent in its own context window as step zero, deleting the incumbent and its tests before the build session ever reads them.

## Scope

- In scope (must-have): the `incumbent:` frontmatter key and its decision rule; `grill-engineer` setting it at spec-it and holding an in-session verdict on the build-now path; `implement-task` gating on its absence and running demolition as step zero; a new `implement-task/references/demolition.md` execution discipline; a new write-capable `.claude/agents/demolition.md`; the type-error connection map and the shrinking red-state contract; the demolition record's filter, four categories, and forward-requirement phrasing rule; upstream cascade prose in `grill-product`, `grill-design`, and `grill-initiative`; `tdd` run-scope statement; `project-init` typechecker detection and offer; `settings.json` permissions, `.gitignore` scratch path, `fork-points.md` couplings, skills `README.md` blurbs, and the `CHANGELOG.md` entry.
- Nice to have: a `docs/adr/` record for the write-capable-agent precedent, deferred unless the build surfaces a genuine trade-off worth freezing.
- Out of scope (non-goals, named so the task does not expand silently): any change to how slices are authored or ordered beyond the red-state contract; a demolition path for documents or context files (`grill-initiative`'s estate reconciliation already owns that); automatic rollback tooling beyond git; changing `review-board` seats or checklists; measuring whether the mechanism actually reduces Guard-and-Go rates in this suite, which needs usage this change does not have yet.

## Requirements

- `incumbent:` is required frontmatter on every task file at `status: scoped`, taking exactly one of `none` (greenfield, nothing exists to demolish), `replace` (the existing implementation dies and demolition runs), or `extend` (built on in place, no demolition); captures omit the key entirely alongside the other scoped sections.
- The key names the mechanism, never the genre of work: a refactor rewriting a module behind an unchanged interface is `replace` with a strict contract, while a rename-only refactor is `extend`, and genre words force the build to interpret where the label exists to remove interpretation.
- `incumbent:` is orthogonal to the existing `type:` key and never overloads it — a `chore` can be `replace` and a `feature` can be `extend`.
- An `extend` verdict carries a one-line why in Design decisions, because it is the escape hatch the measured bias reaches for and an unreasoned `extend` is indistinguishable from an unexamined one.
- A missing `incumbent:` key on a `status: scoped` task is a hard gate in `implement-task` step 1, refusing the build and routing to a grilling session, joining the existing refusals for `TBD (needs grilling)` in load-bearing sections and for a surface-bearing task with neither `design:` nor a governed-verdict.
- Demolition runs in a separate agent context, never inline in the build session, because the firewall is the mechanism: a build session that never reads the incumbent implementation has nothing to anchor on.
- The demolition agent executes a mandate and never authors one: which surface dies and which regions survive as carve-outs arrive from the task file, and an agent choosing what is worth keeping is authoring composition at build time with no design authority.
- Deletion is ruthless wherever deadness is evidenced by LSP find-references plus a repo-wide grep, and stops only where evidence is unavailable — dynamic access, feature flags, serialized handler names, and public API surface stay per the `CLAUDE.md` suspected-dead-unverified rule, reported rather than removed.
- Tests for the demolished surface are deleted with it, because a green test asserting the old behavior makes keeping the old implementation the only way to stay green; before deleting, each test is checked for a smuggled behavioral guarantee per `tdd/SKILL.md:39`, and every guarantee found becomes a line in the demolition record.
- The demolition record admits only material passing this filter: anything the code alone knows, that no other artifact can state, and no design or brief artifact overrules, written so it cannot be pasted back.
- An overrule is a stated contradiction in the design or brief with its location cited, never silence — silence preserves, because a wrongly-preserved contract is a visible line someone can challenge while a wrongly-dropped one breaks an external consumer in production.
- The record carries exactly four categories: boundary contracts something outside the demolition zone depends on; edge cases with their provenance from `git log` or `git blame`, with unsourced conditionals listed as unexplained rather than preserved as requirements; the suspected-dead-unverified set the agent declined to delete and why; and cropped screenshots of declared carve-outs.
- The record excludes verbatim code, anything the design artifact states, anything the type errors already carry, and structural description of the old surface, which is the incumbent's curation entering through the back door.
- Every record line is phrased as a requirement on the new build, never a description of the old one, and a line that cannot be phrased that way has failed the bar and is cut.
- Carve-out screenshots ride the existing `docs/assets/<artifact-slug>/` plus `source:` frontmatter path rather than a parallel mechanism, cropped to the exact surface and labeled with what each covers, and classified before storage per the data-handling rules.
- The demolition record lives in a gitignored scratch path inside the worktree, is dead when the task lands, and any line that proves to be durable project knowledge routes to `domain-modeling` at `implement-task`'s end-of-task shape check.
- Demolition commits its own explicitly-named red state; the type errors it leaves are recorded as the connection map, each subsequent slice must shrink that set and introduce no errors outside its own scope, and the set is zero before the human QA gate.
- Per-slice validate no longer requires a green project typecheck while the connection map is non-empty; lint and the slice's own test files stay green per slice, since deleted files produce no lint errors and deleted tests go with their code.
- `tdd` states its execution scope: run the tests covering the seam under test plus its direct consumers, lint only touched files, and the full suite exactly once at the end of the work — a dependency-shaped bound, not a directory-depth one, since depth means a whole app in one layout and a single util in another.
- `project-init` treats a missing project typechecker as an agenda item rather than a recorded fact, states the cost, does the cheap version inline where the stack allows it, and hands out a captured task where adoption is a migration.
- Every slice touching `.claude/skills/` loads `skill-creator` first per the `guard-skill-edit` hook, and the change lands with its README blurbs, `fork-points.md` couplings, gut-check prompts, and a `CHANGELOG.md` entry per the template-dev rules.

## Acceptance criteria

- [ ] `implement-task` pointed at a `status: scoped` task with no `incumbent:` key refuses to build and routes to a grilling session, naming the missing key.
- [ ] `implement-task` pointed at an `incumbent: replace` task runs demolition before the first slice, and the build session's own context never contains the demolished implementation's body.
- [ ] The demolition agent announces a manifest naming what dies, what survives, and what it verified has no references, then proceeds without a confirm gate, matching the deep plan's proceeding-unless-interrupted window.
- [ ] A demolition run over a surface with a dynamically-referenced handler leaves that handler in place and reports it as suspected dead, unverified.
- [ ] The demolition record contains no code blocks, and every line reads as a requirement on the new build rather than a description of the old one.
- [ ] A boundary contract the design artifact explicitly contradicts is absent from the record, and one the design is merely silent on is present.
- [ ] After demolition on a TypeScript project the recorded type-error set is non-empty, each subsequent slice reduces it, and it reaches zero before the QA gate.
- [ ] `grep -rn "incumbent:" .claude/skills docs` shows the key documented in the task template, `grill-engineer`, and the scoped-task example, with no stale genre vocabulary (`demolition:`, `rebuild:`, `refactor:`) anywhere in the payload.
- [ ] `project-init` run against a JS project with no typechecker raises it as a plan item with its cost stated, and against a `uv` Python project offers the cheap `pyright` wiring inline.
- [ ] `pnpm format:check` passes, the skills `README.md` blurbs and stage map match shipped behavior, `fork-points.md` carries the new couplings, and the `CHANGELOG.md` entry is present.
- [ ] Gut-check prompts run in fresh sessions confirm each edited skill triggers and behaves as intended, per `skill-creator`'s handoff.

## Dependencies

None external. The demolition agent needs the project's UI verification tool for carve-out screenshots (`playwright-local` per the shipped `CLAUDE.md`), which is inert on projects with no UI.

## Risks / open questions

- [ ] Whether a subagent declaring `Edit`, `Write`, and `Bash` inherits the session's permission decisions or prompts independently is unverified; all six existing agents are strictly read-only, so this is the suite's first write-capable agent and the first that deletes. Verify before wiring, and fall back to the main session executing the agent's manifest if a subagent cannot delete cleanly — that fallback keeps the mandate but loses the context firewall, which is the whole mechanism, so it is a degraded design rather than an equivalent one.
- [ ] Whether a write-capable subagent can also reach MCP tools for screenshots is unverified; `research-analyst` proves read-only agents can, but the combination is untested.
- [ ] The scratch path for the demolition record is undecided. `.gitignore` already lists `.ai/worktrees` and `.ai/implementations`, but the directory does not exist and nothing in the payload references either path, so they are unexplained residue — decide at build whether to reuse `.ai/` or mint a named path, and remove the dead entries if they are confirmed orphans.
- [x] Resolved at slice 5: `incumbent:` does not go on the design artifact. The design session states the replace-or-extend judgment in its hand-off, where it is cheapest to make, and `grill-engineer` stays the single writer of the key — so nothing recorded upstream can go stale when an artifact is legitimately amended mid-build, the exact failure `implement-task` already names for copied contracts. `grill-initiative` needed no edit either: its Doctrine subsection already binds cross-cutting product constraints and its worked example already carries a replacement doctrine.
- [ ] No published source, vendor or academic, addresses whether splitting demolition from construction into separate agents helps or hurts; both bias papers establish the symptom and neither tests this mechanism. The context-firewall reasoning is sound and unvalidated, so treat the first few real runs as evidence and be willing to collapse the agent back into a procedural step if the firewall buys nothing.
- [ ] Over-deletion recovery rests on git plus a widening type-error set as the immediate readout; on stacks with no typechecker that readout is absent and the agent's own reference audit is the only net, which is weaker. `project-init`'s typechecker offer narrows this over time but does not close it for existing projects that decline.

## Design decisions

- The label names the mechanism rather than the genre of work, because `implement-task` needs exactly one fact — does the incumbent survive — and genre words like refactor map onto both answers depending on scope, reintroducing the interpretation step the label exists to remove.
- Absence of the label is a gate rather than a default, because a default of no-demolition hands the win to the measured bias on precisely the tasks nobody examined, and captures written by `capture-task` carry no grilling behind them by design.
- `grill-engineer` is the universal chokepoint for setting the label, not `grill-product` or `grill-design`: every path to a buildable task — brief workstream, design artifact, or bare capture — passes through its spec-it exit, which is the only place `captured` flips to `scoped`. Need for demolition is orthogonal to need for a product conversation, and chores, dependency migrations, and refactors are the purest replace cases in the taxonomy while never touching product.
- Upstream tiers carry the intent as prose only, no machinery: the brief states replacement in Position and Out of scope per `grill-product`'s position-compact doctrine, the initiative can bind it as Direction doctrine since it is a product constraint, and neither writes delivery machinery into an artifact.
- The separate agent is a context firewall, not a division of labor. Its value is that the build session never reads the incumbent implementation, so the anchor the research measures is absent rather than resisted; a procedural step inside the build session keeps the code in context and asks the biased party to resist itself.
- The record's filter carries an overrule clause because without it the record becomes a back door: a contract the new design explicitly rejects would survive on the grounds that only the code knows it, quietly restoring preservation through the artifact meant to prevent it. Silence does not overrule, on cost asymmetry — a wrongly-kept contract is a challengeable line, a wrongly-dropped one is a production break.
- The record's most valuable category is provenance-backed edge cases, and archaeology is the demolition agent's highest-value capability. Spolsky's argument that code encodes hard-won bug fixes is correct and incomplete: code also encodes accidents, and code alone cannot distinguish them, while `git log` and `git blame` on a file about to disappear partially can — a question no other actor in the chain is positioned to ask.
- Type errors are the demolition-to-build handoff, replacing any structural description the record might otherwise carry. Every red edge is a place something surviving still expects what died, generated by the compiler rather than inferred by a session, which is both more reliable and immune to the incumbent-curation problem that makes prose descriptions poisonous.
- The red-state contract makes middle-of-task red legal but attributable: the error set shrinks monotonically and no slice introduces errors outside its own scope, so "it is red anyway" cannot become cover for a real regression.
- Ruthlessness is bounded by evidence rather than by caution, since a model told to be ruthless will not reliably feel cautious in the right places. The `CLAUDE.md` suspected-dead-unverified category is the existing, non-judgment-based brake and it transfers directly.
- Carve-out screenshots reuse `grill-design`'s Supplied-path machinery — `docs/assets/<artifact-slug>/`, `source:` frontmatter, per-breakpoint labeling, classification before storage — rather than a parallel mechanism, and `implement-task` already knows how to diff a render against them. The agent captures the image; the design decides the subject.
- Build-time deviation, slice 3, pending ratification: carve-out screenshots are captured by the dispatching `implement-task` session before the agent runs, not by the agent itself as originally scoped. The dispatching session already has the project's UI tool wired and named in `CLAUDE.md`, so the agent avoids hard-coding a tool name that is a per-project fork point, and driving a running app yields pixels rather than source, so the firewall holds either way. The design still decides the subject; only the actor moved.
- Build-time finding, slice 3: no `settings.json` change is needed — `Bash`, `Edit`, and `Write` are already blanket-allowed, so the agent functions unprompted. The corollary is that its `rm` is unguarded, which is why the discipline mandates `git rm` without `-f`: only tracked, unmodified files delete, uncommitted work in the zone halts the run, and everything removed stays recoverable in the index.
- This task is `incumbent: extend` (dogfooding the rule it introduces, one-line why included): every edit adds behavior to skills whose current instructions stay correct, and no existing mechanism is being replaced — the two new files are net-new surface, not successors.
- Reference implementations: `grill-design`'s fidelity contract for the store-classify-transcribe sequence and its stated reason that sequencing is load-bearing; `grill-initiative`'s estate reconciliation for planned destruction presented as a reviewable classification; `tdd/SKILL.md:39` for the check-before-delete discipline at test scope; `research-analyst.md` for the agent-definition shape, inverted from read-only.

## Test strategy

This repo ships no application code, so validation is `pnpm format:check` plus the acceptance criteria exercised as manual QA at the real seams, and `skill-creator`'s gut-check handoff is the substitute for an automated suite: each slice touching a skill closes with fresh-session test prompts covering should-trigger, should-not-trigger near-misses, and the expected behavior stated so the user can judge pass or fail. The mechanism itself is exercised end to end against a real `incumbent: replace` task in an instance rather than simulated here, because a demolition run over an empty workspace proves nothing. Payload-wide greps stand in for consumer checks, since LSP find-references does not reach markdown: the stale-vocabulary and key-presence greps in the acceptance criteria are the regression net.
