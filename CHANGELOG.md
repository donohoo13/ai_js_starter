# Changelog

Template releases, newest first. Each entry carries three parts: **what** changed, **why**, and **adaptation notes** for instances whose posture diverges from the shipped defaults (compliance regimes, external trackers, collapsed monorepos). A release is a git tag (`vX.Y.Z`) on `main` matching the entry heading; the `sync-template` skill in an instance walks unapplied entries oldest-to-newest (later releases assume earlier ones landed) and negotiates each into the instance's own posture. In an instance this file is template residue: `project-init` stamps the template lineage into `CLAUDE.md` from the top entry here, then deletes this copy.

## v1.2.1 — 2026-07-30

- **What**: Serves the two npx-launched plugin MCP servers from the project `.mcp.json` instead of their plugins. `context7` becomes a keyless remote HTTP stanza (`https://mcp.context7.com/mcp`) and the plugin leaves `enabledPlugins`, since it shipped nothing but the server; `chrome-devtools` becomes a `pnpm dlx chrome-devtools-mcp@1.6.0` stanza named identically to the plugin's server so project scope shadows the plugin's npx spawn by name while the plugin stays enabled for its six skills. Tool prefixes retarget (`mcp__plugin_context7_context7__*` → `mcp__context7__*`, `mcp__plugin_chrome-devtools-mcp_chrome-devtools__*` → `mcp__chrome-devtools__*`) across `settings.json` permissions, the `CLAUDE.md` MCP Tools section (whose playwright/firefox prefixes are also corrected to the hyphenated spellings `settings.json` actually allows), and the `research-analyst` agent tool list; the context7 allow entries enumerate the two verified tools (`resolve-library-id`, `query-docs`) rather than a wildcard, so a tool the remote endpoint starts serving later prompts for approval instead of auto-running. `doctor.sh` gains an ambient-Node-vs-`.nvmrc` drift warning, `check-install.mjs`'s accepted-cost header grows the npx blast radius, `template-dev.md` records the context7 carve-out in the machine-local disable list, and `package.json` `version` → 1.2.1. The env matrix's Alpine cell flips from expected-failure to the same pass assertions as the glibc cells, retiring the `musl-fail` mode from `run.sh`/`assert.sh` entirely, and the musl story is rewritten across `check-install.mjs` (header and guard-message text), the battery case label, `README.md`'s network note, and `fork-points.md`: musl provisioning works, and the delete-the-block posture becomes a supported opt-out rather than a necessity.
- **Why**: Claude Code spawns plugin MCP servers with cwd at the project root, both plugins spawn via `npx`, and npm enforces the cwd project's `devEngines` there while treating `onFail: "download"` as an error — so any shell whose ambient Node differed from the exact v1.2.0 pin killed both servers instantly with `EBADDEVENGINES`, surfaced only as an opaque `-32000` in `/plugin`. Measured, not assumed: the MCP logs show the error verbatim from a `v24.17.0` shell against the `24.18.1` pin, the migrated `context7` stanza answered real queries live from that same drifted session (tool names `resolve-library-id`/`query-docs` confirmed against the endpoint, server v3.2.5), and the doctor warning fires under a mismatched shim and stays silent under a matching one. `pnpm dlx` is immune because pnpm implements `onFail: "download"` by downloading the pinned runtime, and remote HTTP never touches Node — the same reasoning that already shaped the `playwright-local` and `firefox-devtools` stanzas. The per-server plugin disable (`/mcp` toggle into `~/.claude.json`) is per-machine and unshippable, which is why shadowing carries the chrome-devtools fix. Keyless Context7 has documented-but-unquantified "low" rate limits; the escalation path (free `ctx7sk` key as an `Authorization: Bearer` header via `${CONTEXT7_API_KEY}` expansion) is documented at the stanza's `CLAUDE.md` bullet and deliberately left unwired until limits actually bite. The musl flip is upstream drift caught mid-release, measured twice on 2026-07-30: the matrix's Alpine cell passed on `main` at 03:04 UTC with pnpm 11.7.0 refusing resolution (`ERR_PNPM_NO_RESOLUTION_MATCHED` against a variant list with no musl entry) and failed by 18:47 because the same pinned install now succeeds — reproduced on untouched `main` via `workflow_dispatch`, so it is not this release's diff — and pnpm's runtime-variant manifest now carries `linux-x64-musl`/`linux-arm64-musl` entries pointing at `unofficial-builds.nodejs.org`. Verified on `node:22-alpine` before flipping the cell: the full pass assertions hold (`pnpm exec`/`pnpm run` report the pinned version, bare `node` keeps the image's), and the provisioned binary is musl-native per `process.report` (no `glibcVersionRuntime`) — Alpine executes no glibc binary without a compat layer, so successful execution is itself the proof. The cell stays in the matrix as a pass cell because a server-side manifest regression would silently re-break musl installs, and an asserting cell is the only thing that would notice.
- **Adaptation notes**: Take the two stanzas, the `enabledPlugins` removal, and every prefix retarget as one unit — stanzas without the retargets (or vice versa) leave sessions pointing at tools that no longer exist. An instance whose developers user-installed either plugin keeps working because project scope wins same-name collisions, but verify in `/mcp` that exactly one `chrome-devtools` connects (plugin dedup by endpoint is the documented ambiguity; if both spawn, fall back to the per-machine `/mcp` toggle). An instance pinning a different `chrome-devtools-mcp` version updates the dlx pin; an instance already carrying a Context7 API key adds the Bearer header via env expansion rather than a literal. The doctor drift check reads `.nvmrc` at the repo root; instances that relocated the pin adjust the path. musl instances that deleted `devEngines` per v1.0.1/v1.2.0 may now re-adopt the pin, with eyes open that the musl variants are community `unofficial-builds.nodejs.org` artifacts pinned by lockfile integrity rather than release-signed tarballs — the opt-out posture stays fully supported and the guard still reads an absent block as deliberate, so re-adoption is a choice, not a migration. Lockfile hand-review widens accordingly: `node@runtime:` URLs legitimately name `unofficial-builds.nodejs.org` for musl variants, and restricted networks add that host when musl installs matter. The `template-dev.md` amendment is template residue and never syncs.

## v1.2.0 — 2026-07-29

- **What**: Moves the template onto a pnpm 11 + Node 24 LTS version-management model, fixes two `from-instance` defects (#14, #15), and clears the last of the v1.0.7 residue. **Pins**: `packageManager` `pnpm@10.32.1` → `pnpm@11.7.0`, and the Node pin from Current-only `26.5.0` to active-LTS `24.18.1` across all four sites (`.nvmrc`, `engines.node` `>=24.18.1 <25`, `devEngines.runtime.version`, regenerated `pnpm-lock.yaml`), plus `package.json` `version` → `1.2.0`. **Guard** (`scripts/setup/check-install.mjs`): the `engineStrict`×`devEngines` hard-fail is scoped to pnpm `<=10` (the major is parsed from the `npm_config_user_agent` already read for the pnpm-only check), because on pnpm 11 the runtime is provisioned before the engines check and the pairing installs cleanly; the exact-vs-range rationale is corrected to pnpm 11's `ERR_PNPM_IGNORED_BUILDS` failure, the wrong-Node check is documented as advisory on pnpm 11 (preinstall runs under the provisioned runtime), and the header's version-specific measurement logs move here to the changelog, leaving mechanism and causal why. A dependency-free verification battery (`scripts/test/check-install.battery.mjs`, 10 cases) and a `fork-points.md` entry (pnpm 11+ instances may keep `engineStrict: true` alongside `devEngines`) accompany it. **Conventions** (`CLAUDE.md`): a `pnpm exec node` rule (one-off Node runs on the pinned runtime, not ambient) and a corepack-migration rule (Corepack is bundled through Node 24 and removed from 25+, so a bump off Node 24 migrates pnpm activation in the same change); the Node-pin bullet reframes `.nvmrc` as read by the guard, CI, and nvm but never pnpm. **Docs**: the README gains a Mac/Linux quickstart (Homebrew, or the Apple-Silicon standalone installer, then `pnpm install`) with the Node-25 caveat at point of use, and #14 is fixed — the skills README no longer calls `curate-context` hook-enforced in the chain block and stage map (`skill-creator`'s row is left, since `guard-skill-edit` survives). **Tests**: a Docker environment matrix (`scripts/test/env-matrix/`) proving pnpm provisions and uses the pinned Node across a mismatched-major image, a no-Node image, and a musl image (expected failure), plus the repo's first CI workflow (`.github/workflows/checks.yml`) running the guard battery and the matrix. The v1.0.7 steering-doc residue strip (eight hook-removal references rewritten to present tense, the `guard-main.mjs` example tag genericized) and the `template-dev.md` provenance rule (version references live only in the history records) land here too.
- **Why**: The `Unsupported engine` warning on every pnpm command was a pnpm-10 artifact of pinning bleeding-edge Current Node (`26.5.0`, LTS only in October 2026) ahead of the LTS (`24.x`) that developers and CI actually run. On pnpm 11 the `devEngines` runtime is provisioned before lifecycle scripts and every pnpm-routed command — `install`, `pnpm run`, `pnpm exec` — runs under it regardless of ambient Node, so the wrong Node is unreachable through pnpm by construction and the warning disappears. Measured, not assumed: from a container with ambient Node `v22.23.2` and the `24.18.1` pin, the preinstall guard, `pnpm exec node`, and `pnpm run` all reported `v24.18.1` while bare `node` stayed `v22`, and `pnpm install` printed no engine warning; the no-Node `ghcr.io/pnpm/pnpm` image provisioned the pin from nothing. That retires the two standing risks — a silent wrong-Node run (now impossible for pnpm-routed commands) and environment friction (the pin is a version everyone can be on) — with the `pnpm exec node` convention closing the one remaining gap, bare `node`. #15 and the v1.0.7 residue are the same defect class: a pnpm-10 measurement asserted as universal present fact. The guard encoded the `engineStrict` deadlock as always-true; pnpm 11 reordered the engines check after the runtime switch so the pairing coexists, and the fix mirrors the residue strip — state current behavior, scope the version-specific claim, move the measurements to the changelog. `engineStrict` stays off because the Node consistency it would nominally strengthen is already guaranteed by `devEngines` on pnpm 11; it only blocks incompatible dependency engines, orthogonal to the goal. Corepack is correct on Node 24 (bundled), so it is used as-is and the Node-25 removal is recorded as a triggered migration rather than a standing avoidance — future-proofing a tool that still works would be the speculative seam this repo's own rules warn against. #14 was a v1.0.7 miss: two `curate-context` lines kept saying "hook-enforced" after the hook was cut, contradicting the file's own blurb.
- **Adaptation notes**: The pins live in `package.json` and `pnpm-lock.yaml`, which `sync-template` offers — an instance carrying its own Node/pnpm pins negotiates this hop rather than applying clean: take the guard, convention, and doc changes, keep your pins. An instance still on pnpm `<=10` keeps the guard's deadlock hard-fail (the major-scoping preserves it) and does not adopt the pnpm 11 pin unless it wants to; an instance on pnpm 11+ may now also set `engineStrict: true` alongside `devEngines` for dependency-engine blocking, which the guard no longer refuses. The guard rewrite, the `pnpm exec node` and corepack conventions, the skills-README #14 fix, the README quickstart, the verification battery, the env matrix, and the CI workflow are all payload that syncs; the env matrix's images and the workflow's steps assume Docker and the shipped stack, so an instance adapts them (its own base images, its own CI cadence — the matrix pulls images and downloads a runtime, so it is not free per PR). musl instances keep deleting the `devEngines` block, the posture the guard already treats as deliberate and the matrix's third cell documents (pnpm 11.7.0 fails it with `ERR_PNPM_NO_RESOLUTION_MATCHED`, since nodejs.org publishes no musl variant). The Node pin tracks the active LTS: `24.18.1` today, with Node 26 reaching LTS in October 2026 and Node's annual-LTS model starting at 27 — a future bump follows the corepack-migration rule in `CLAUDE.md`. The `template-dev.md` provenance rule, the `fork-points.md` entries, `project-init/`, and this changelog stay inside `sync-template`'s residue exclusion and are never offered to instances.

## v1.1.0 — 2026-07-29

- **What**: Opens the reverse direction of the template relationship and stops the forward one from leaking. `sync-template` Phase 1's release diff gains a pathspec exclusion covering the template's own residue — `CHANGELOG.md`, `.claude/rules/template-dev.md`, `.claude/skills/project-init/`, `docs/tasks|adr|designs|briefs`, and `CONTEXT.md`/`ARCHITECTURE.md`/`CONTEXT-MAP.md` — mirroring the set `project-init`'s Phase 4 clears, with `docs/company/` deliberately absent because it is payload skeleton that stays; both files gain a maintenance line stating the two lists move together, and `fork-points.md` records the coupling. A new `template-feedback` skill ships as the child-to-parent reporting channel: strictly user-invoked through `disable-model-invocation: true`, it validates a caller's complaint against the session that produced it via a disqualifying pre-flight (lineage against the template changelog, `docs/template-sync-log.md` rejections, local-fork state), gates hard on a narratable trace, attributes to one of five verdicts (`defect`, `gap`, `misfit`, `upstream`, `not-the-template`), and files a scrubbed GitHub issue behind one non-skippable confirm, with `assets/issue-template.md` defining the body. `project-init` now names both `sync-template` and `template-feedback` as the machinery that survives init, `.claude/skills/README.md:30`'s "no GitHub issues anywhere in the chain" gains its template-boundary carve-out, and `ship-pr` is restated as the _work chain's_ one door to the remote rather than the only one.
- **Why**: The release diff was unscoped, so every release offered instances files that `project-init` had deliberately deleted from them — and this is measured rather than predicted: `git diff --name-only v1.0.6 v1.0.7` returns `CHANGELOG.md` plus both `project-init` files, meaning v1.0.7 as published would have offered every instance a reinstall of the skill whose final act is deleting itself, and a template ADR dropped into a project's `docs/adr/` reads to `domain-modeling` as that project's own architectural decision. The feedback skill exists because the relationship was one-directional by construction: instances pulled releases and had no route home for what they learned, so a defect found in a child either got fixed locally as a silent fork or was lost. It is user-invoked rather than AI-detected because a session appraising its own output for signs of user frustration either never fires or fires as deflection, filing template debt for its own bad reasoning; the caller recognizing something is the only reliable trigger. The five verdicts exist so the queue stays worth reading — friction feels like a defect in the moment, and a channel that files everything as `defect` or `gap` fills with issues resolving to working-as-intended, so reaching `misfit` (the default is right, this project differs) and `not-the-template` is the triage's actual work. `misfit` is the highest-value output because it grows `fork-points.md` from real evidence instead of speculation about what future projects might need.
- **Adaptation notes**: The exclusion cannot protect the release that introduces it — an instance runs its _own_ pre-v1.1.0 copy of `sync-template` for this hop, so reject any residue hunks by hand in this one diff; from v1.1.0 onward it is automatic. `template-feedback` needs issues enabled on the template repo plus five labels (`from-instance`, `defect`, `gap`, `misfit`, `upstream`) before it can file, and it fails loudly rather than silently when they are missing. Its `gh` calls are the one inverted platform coupling in the suite: they target the _template's_ repo, so an instance on GitLab or Bitbucket leaves them pointing at GitHub and only retargets them if the template itself relocates — `fork-points.md` carries the warning, because retargeting them to the instance's own platform severs the channel silently. An instance wanting no feedback channel deletes the skill directory, its README section, and its stage-map row together. Instances that forked `sync-template` add the exclusion to their own Phase 1 and keep it aligned with whatever their `project-init` residue list became; an instance whose docs live outside `docs/` adjusts the excluded paths to match, since the exclusion is written as literal pathspecs rather than derived.

## v1.0.7 — 2026-07-29

- **What**: Cuts the guard-hook suite from five to three and moves what the biggest one enforced into prose. `.claude/hooks/guard-context-edit.mjs` (309 lines) and `.claude/hooks/guard-adr-links.mjs` (169 lines) are deleted with their `settings.json` entries; `guard-main`, `guard-secret-read`, and `guard-skill-edit` stay. The `CLAUDE.md` Skills bullet that described the context gate is rewritten to carry the ownership itself — `curate-context` for the prescriptive files, `domain-modeling` for the descriptive ones — plus the admission bar the hook never checked: every addition, change, and deletion names what a future session does differently because the line exists, or gets cut, with deletions stated to the user rather than landed silently. A second new bullet in Development records that ad-hoc Bash tool commands run under zsh, which does not word-split an unquoted `$VAR` while it does split an unquoted `$(cmd)`. Eleven references across six skills are rewritten rather than clause-deleted, since the thesis inverted from "a hook enforces this" to "this description is the enforcement": `curate-context`'s description frontmatter now states the trigger as the file path itself, `domain-modeling` and its `ADR-FORMAT.md` take ownership of the ADR frontmatter contract outright, and `project-init`'s fork-points entry redirects a project that wants ADR frontmatter checked mechanically to a lint rather than a PreToolUse hook. Three skills deliberately keep a sentence naming each removed hook and why it went, so neither gets re-added.
- **Why**: The hooks' founding premise — that skill descriptions alone undertrigger, so a deterministic backstop is needed — was the one claim in this repo asserted rather than measured. Measuring it across all 1,404 Claude Code transcripts on the development machine settles both removals and both keeps. `guard-context-edit` produced 195 blocks over 26 sessions, but blocks are not catches: collapsing retries gives 57 distinct file-and-session pairs, and stripping test fixtures leaves roughly 18 real files — 6 `README.md`, 4 `CLAUDE.md`, 3 `BRAND_DESIGN.md`, 2 `CONTEXT.md`, and one each of `CLAUDE.local.md`, `CONTEXT-MAP.md`, and `ARCHITECTURE.md`. The distinction that decides it is what a skipped discipline actually costs per file: only the files that steer future sessions (`CLAUDE.md`, `CLAUDE.local.md`, `.claude/rules/`) fail silently and compound, because a wrong rule there misdirects every later session and never announces itself, while a bad `README.md`, `BRAND_DESIGN.md`, or `ARCHITECTURE.md` is visible on sight. Catches on the silent class: five. That is the return on 309 lines that consumed two of the four preceding releases (v1.0.3's scope and subagent fixes, v1.0.6's prefilter deletion) and, after v1.0.6, ran on every Edit and Write in every session. The counter-argument is also correct on its own terms and is why the replacement is a rule rather than a smaller hook: a hook firing 18 times means the descriptions failed 18 times, and the hook hid that failure instead of fixing it, so removing it converts a masked defect into a visible one. What the hook could check was always weaker than it appeared — it verified that a skill was loaded, never that its discipline was followed — so the thing it actually bought was the skill's instructions entering context, which is exactly what a well-written description buys at no maintenance cost. `guard-adr-links` goes for a different and simpler reason: it fires only on writes made through Claude Code, so a human editing an ADR in an editor bypasses it completely, which means it never enforced the convention at all — it taxed one author for it, at 48 blocks over 15 distinct pairs in 4 sessions. It is also the only hook that validated file _contents_ rather than process, and a content check belongs in a lint that runs over every ADR regardless of author. This repo ships no `docs/adr/` directory, so it has never fired here at all. The two keeps are decided by the same evidence rather than by taste. `guard-skill-edit` is 46 lines and one path test, has never needed a fix in any release, and caught 12 distinct cases across 11 sessions — roughly once per session that touched a skill, on the same silent-compounding class as `CLAUDE.md`, since a skill with a broken description undertriggers in every future session without telling anyone. It is 46 lines against 309 for the same job, and the entire difference is that `.claude/skills/` is an unambiguous path while `CLAUDE.md` is a basename that can be anywhere — that ambiguity is what forced the repo-scoping, worktree git identity, symlink canonicalization, and vendored carve-outs the removed hook accumulated. `guard-main` is the most load-bearing guard in the suite at 34 distinct catches across 29 sessions, and it handles the compound forms correctly, verified against `&&`, `;`, `||`, a `for` loop, `--force`, `--force-with-lease`, `--all`, colon refspec deletes, and `git push origin HEAD`; its one real bypass is a git command nested inside `bash -c`, `sh -c`, or `eval`, which is left unclosed deliberately because parsing nested shell quoting costs more than GitHub branch protection, which covers the push case server-side for every author. The zsh bullet is unrelated to the hooks and lands here because it was measured in the same session: the Bash tool runs zsh 5.9, and zsh's split rules are asymmetric, so `for p in $(get_pids)` iterates per item while the natural refactor `PIDS=$(get_pids); for p in $PIDS` iterates once over the whole string. Verified in the tool's own shell — command substitution splits, parameter expansion does not, `${=PIDS}` and zsh arrays split, and `printf '%s\n' $PIDS` does **not** fix it, because `printf` inherits the same non-split and receives one argument. That last point is why the rule names the wrong fix explicitly: the failure already cost real teardown work in an instance, and the remedy circulated for it was itself broken. The failure mimics success, which is the shape worth warning about — `kill` on a space-joined string errors into an `|| echo "already gone"` branch that reads as a clean teardown, so the rule says to verify the result rather than the exit status. Shipped scripts are unaffected, carrying `#!/usr/bin/env bash` shebangs, and all three surviving hook prefilters quote every expansion, confirmed by running the identical `case` pattern under bash 3.2.57, zsh 5.9.2, and `sh` with identical results.
- **Adaptation notes**: Instances delete both hook files and both `settings.json` entries, then take the two `CLAUDE.md` bullets and the eleven skill rewrites — the skill edits are what keep the discipline reachable once the enforcement is gone, so an instance that deletes the hooks and skips them ends up with neither mechanism. An instance that measured its own transcripts and found a materially higher catch rate on `CLAUDE.md`-class files keeps `guard-context-edit`: the removal argument is a measurement, not a principle, and a team that edits root context files far more often than this machine's history shows may land on the other side of it. The narrower option that was considered and not taken is available to such an instance — gate only `CLAUDE.md`, `CLAUDE.local.md`, and `.claude/rules/`, matched by path rather than basename, which collapses the hook to roughly `guard-skill-edit`'s size because path matching needs none of the repo-scoping, worktree identity, or canonicalization that basename matching forced. Instances wanting the ADR frontmatter contract still enforced add a lint over `docs/adr/` rather than restoring the hook, so the check covers human-authored ADRs too; that is the defect that removed it, not its strictness. Instances that forked either hook simply drop their fork. The zsh bullet applies to every instance whose developers drive Claude Code on macOS, where the Bash tool's shell is zsh regardless of what the repo's scripts use, and it is worth landing even in an instance that rejects everything else in this release. Instances on a platform where the Bash tool runs bash reword it to name their own shell rather than dropping it, since the asymmetry is the trap and the reader needs to know which side they are on.

## v1.0.6 — 2026-07-29

- **What**: Closes the `guard-context-edit` prefilter's case-variant hole that v1.0.3 recorded and left open, by deleting the prefilter rather than extending it. The `Edit|Write` entry in `.claude/settings.json` becomes `node "$CLAUDE_PROJECT_DIR/.claude/hooks/guard-context-edit.mjs"` with no shell wrapper at all — the `input=$(cat); printf` plumbing went with the `case`, since the hook reads stdin directly. The hook's matching logic is untouched; the two comment blocks in it that described the prefilter are rewritten to describe what now decides, and why nothing upstream can. The driving task file `docs/tasks/2026-07-29-bug-context-guard-prefilter-case.md` moves to `done` with the decision, the measurement, the rejected alternatives, and the follow-ons recorded on it, and v1.0.3's note about the hole now points here.
- **Why**: The prefilter enumerated literal case variants and forwarded only those, so a spelling outside the list never reached the hook and the hook's own case-insensitive matching never got to run — a silent failure, since a guard that does not fire reports nothing. The task file named three ungated spellings; running every governed spelling through the command string read straight out of `settings.json` found six, `Context.md`, `Ui_Ux.md`, `docs/ADR/`, `Context-Map.md`, `Brand_Design.md`, and `Claude.local.md`, the last of which is the sharpest illustration of why the list approach fails: `CLAUDE.local.md` and `claude.local.md` were both listed and `Claude.local.md` was not, so the list was inconsistent as well as incomplete, and nothing made that visible. The task's own first open question was the whole decision — is a spawn on every Edit and Write actually unacceptable, or is the prefilter a premature optimization — and measuring it settled it: 29.1ms per spawn in the instance where this surfaced and 26.7ms in this repo, hook exiting early on a non-governed path, against a correctness hole no prefilter can close. Deleting it is also the only option that stops the two lists drifting, because a governed basename added to the hook now needs no second edit anywhere; the previous arrangement kept the same names in two languages and they had already drifted, toward not guarding. The three alternatives are rejected on record so they are not re-proposed: bracket classes per character are complete but close to unreadable across ten names; broadening to `*.md*` still misses `.MD` and fires on nearly every payload anyway, since `case` matches the whole hook payload and therefore the file's new content as well as its path; and the hook entry's `if` field does answer the task's second open question — the runner can filter on `file_path` — but it takes one permission-rule string, which cannot express a case-insensitive union of ten basenames, so it reinstates the same silent-miss failure mode one layer over. That path-versus-content property is also why the reasoning had to land in the hook's header: `settings.json` is strict JSON and carries no comment, the header sentence describing the prefilter became false the moment it was deleted, and a false comment is how a prefilter gets re-added. The sibling guards are deliberately left alone and the distinction matters: `guard-skill-edit` and `guard-adr-links` carry prefilters of the same shape but match case-sensitively in their own bodies, so prefilter and hook agree and nothing is dropped between the layers — theirs is a coverage question, not this drop-between-layers bug. `guard-secret-read` is a separate decision on its own merits, since a missed spelling there fails toward exposure rather than an ungated doc edit, and it is `Bash`-matched, so dropping its prefilter would cost a spawn on every shell command rather than every file edit. Verified by executing the shipped command string — read out of `settings.json` at run time so the battery cannot drift from what ships — over thirty cases: all six previously ungated spellings now block, all nineteen previously gated spellings still block, four non-governed paths still pass, and the allow (skill loaded), wrong-skill, unreadable-transcript fail-open, and out-of-repo-scratchpad arms are unchanged. Cost after the change is one Node spawn per Edit and Write, measured at 32.5ms through the shipped command.
- **Adaptation notes**: Instances carrying the shipped entry replace the whole `command` string with the bare `node` invocation; nothing else in the entry changes, and the hook file itself needs no edit beyond the comment rewrite. This is purely a widening — every path gated before stays gated — so the check to run after adopting is not "did anything break" but "does anything now block that a session legitimately needs", which for a case-variant spelling of a governed doc is the intended outcome. An instance that renamed its governed docs to spellings the old prefilter happened to list, and has been relying on that list as the actual gate, discovers here that the hook's arm list is the real registry; reconcile the two before adopting, since the hook is now the only opinion. An instance that added its own governed basename to both lists deletes the prefilter half and keeps the hook arm. An instance on a latency-sensitive setup that genuinely wants a prefilter back keeps one only if it filters on something other than the payload text — the `if` field cannot express the union, and any `case` pattern over the payload reintroduces this bug rather than a milder version of it. Instances that forked `guard-context-edit.mjs` take only the two comment rewrites; instances that already dropped the prefilter for a different reason take nothing but the changelog. Instances carrying `guard-adr-links` should note that `docs/ADR/` is now gated by `guard-context-edit` and still skipped by `guard-adr-links`, whose own body matches case-sensitively — a distinct bug this release does not close.

## v1.0.5 — 2026-07-29

- **What**: Closes a hole in v1.0.1's adaptation notes that bricks instances which followed pnpm's own documentation. That release's notes are extended in place with the `engineStrict` requirement — an instance carrying `engineStrict: true` (or `.npmrc`'s `engine-strict=true`) flips it to `false` in the same change that deletes `nodeVersion` — carrying the measurement, the tradeoff, and the warning not to trust pnpm's settings page on this point. `scripts/setup/check-install.mjs` gains a matching hard-fail: when a `devEngines.runtime` block in `package.json` coexists with `engineStrict: true` in `pnpm-workspace.yaml` or `engine-strict=true` in `.npmrc`, the install stops before the machine check with a named diagnosis, the two ways out, and what each costs. The file's header gains an `engineStrict OFF wherever devEngines is present` item pointing at that check.
- **Why**: v1.0.1 correctly ordered instances to delete `nodeVersion` and move the pin to `devEngines.runtime`, and its notes even anticipated the key — but `nodeVersion` was the only thing holding `engineStrict` harmless, so for any instance that took pnpm's documented advice ("use `nodeVersion` and `engineStrict` in a `pnpm-workspace.yaml` file at the root of the project") the instruction was the direct cause of the brick rather than merely silent about it. With both keys set, the engines check runs against the version pnpm pretends and passes; with `nodeVersion` gone it runs against the developer's ambient Node, before pnpm switches to the `devEngines` runtime, so it refuses the very install that would have downloaded the pin. Measured in an instance on pnpm 10.34.1, macOS/APFS, ambient Node 24.17.0 against a 22.22.3 pin: `engineStrict: true` fails `pnpm install` and `pnpm typecheck` identically with `ERR_PNPM_UNSUPPORTED_ENGINE`, so it is every pnpm command and not just the install, and provisioning the runtime first does not help because the check precedes the switch every time; `engineStrict: false` installs, fetches 22.22.3, and reports it from both `pnpm exec node -v` and `pnpm run` while the shell stays on 24.17.0. pnpm's settings page claims a project's own `engines` field fails the install "regardless of this configuration", which cost a wrong diagnosis before the measurement contradicted it — the notes now say so explicitly, because the next reader will find that line too. The same non-failure is observable in this repo on a different pnpm patch: with `engineStrict` unset, `pnpm format:check` on pnpm 10.32.1 with ambient Node 24.17.0 against an `engines.node` of `>=26.5.0 <27` prints `WARN Unsupported engine` and runs the script, so the doc line is wrong on 10.32.1 as well as 10.34.1. Why the check passes with `engineStrict` off is unknown; the measurement is what both the notes and the guard encode, and neither states a mechanism it cannot demonstrate. Amending v1.0.1 in place is the right mechanism here rather than a workaround: `project-init` deletes an instance's copy of this file and `sync-template` reads the template's tip through `git show template/main:CHANGELOG.md`, so an instance that has not yet applied v1.0.1 gets the corrected notes automatically, while one already past it is exactly who this entry exists for. The `check-install.mjs` half earns its fifteen lines on a narrow but real case, and its limit is stated in the file rather than left for the next reader to discover: it cannot fire in the bricked state at all, because pnpm refuses at command startup and `preinstall` never runs, so a colleague cloning into the pairing still gets pnpm's own message blaming their Node. What it does catch is the pairing on the machine of whoever introduced it while already sitting on the pinned Node — the one state where the configuration is silently latent, and the cheapest place it will ever be fixed. Absent `devEngines` is deliberately not a failure: that is the musl posture v1.0.1 documents, where `engineStrict` is the only Node enforcement the project has and must stay on, so only the pairing fails. The `.npmrc` spelling is checked alongside the `pnpm-workspace.yaml` one because it predates pnpm's move of settings into the workspace file, is still honored, and deadlocks identically — a missed spelling here fails toward a silent brick. Verified against a seven-case battery covering both directions: the pairing under each spelling, `engineStrict: false` with `devEngines`, `engineStrict: true` with no `devEngines`, a commented-out key, an absent `pnpm-workspace.yaml` and `.npmrc`, and a regression confirming the pin-drift check still fires ahead of it.
- **Adaptation notes**: An instance already past v1.0.1 checks its own `pnpm-workspace.yaml` and `.npmrc` for `engineStrict` / `engine-strict` right now, since a repo bricked this way looks like a machine problem and stays misdiagnosed until someone reads the ambient Node in the error. An instance that never set the key needs no config change and takes only the guard. Instances on musl, which delete the `devEngines` block per v1.0.1, keep `engineStrict: true` deliberately — it is their only Node enforcement, the guard's check is scoped to the pairing and never fires without `devEngines`, and this entry asks nothing of them. An instance that genuinely wants dependency-engine blocking more than it wants the runtime download takes the second branch the guard offers, deleting `devEngines` and requiring every contributor to install the pinned Node themselves; both postures are supported, and only holding both at once is refused. An instance whose `engineStrict` sits somewhere the guard does not read — a nested workspace file, a user-level `.npmrc`, a `NPM_CONFIG_ENGINE_STRICT` environment variable — extends `engineStrictSite()` to that site rather than reporting the miss as a false negative. Instances that forked `check-install.mjs` apply the check by hand after the pin-drift block and before the machine check, since it diagnoses a repo bug and must not be reachable only after the machine has already been blamed.

## v1.0.4 — 2026-07-29

- **What**: Fixes three related defects in how a session reports back to the human. A new `CLAUDE.md` Standards rule governs every session-closing message and every mid-session handoff that expects a reply: one consolidated plain-language summary, one bullet per open item, and a bullet the human decides ends in a direct question with the recommendation and its reasoning attached. `review-board`'s consolidated report format (`references/output-format.md`, Part B) is restructured around that same shape — the verdict table stays, the per-verdict prose sections are replaced by a "Your call" list of plain-language decision bullets each ending in a question, a "Noted, no decision needed" list of one-liners for findings nobody is being asked to decide, and an "Evidence" appendix carrying the excerpt, failure scenario, suggested fix, and chair's read for the decision findings only; the separate "Board recommendation" section is gone, since per-finding recommendations now ride in the bullets that ask the questions. `review-board`'s Step 3 replaces "which are safe to defer" with three provenance-decided dispositions — fix in this session, `/capture-task` naming which of its two grounds applies, or noted-no-action — and Step 4 states the report's decision-first contract and the two rules that hold it. Step 6's record commit gains a `captured` outcome spelling carrying the task file path. The skills README blurb and a new tracker fork-point follow.
- **Why**: A closing message that announces "two things want your call" and then asks nothing is unanswerable — the reader cannot tell a question from a status note, and the reply they were supposed to give has no shape. The rule is written as the positive act (name the response each bullet invites; rewrite or cut the ones inviting none) rather than as a ban on status dumps, because the failure is a missing question and not an excess of prose. It lands in `CLAUDE.md` Standards rather than a `.claude/rules/` file because it governs conversational output, which no path can scope: `.claude/rules/` is defined throughout this repo as path-scoped rules, and its only current occupant is `template-dev.md`, which `project-init` deletes — a closing-message rule filed there would ship to zero instances. The review-board half is the same defect in the one format where it is most expensive: the report was ordered by provenance (grouped by verdict, full evidence block per finding), so answering "which findings should I address?" meant reading every excerpt and failure scenario and reconstructing the decision from them, with the actual recommendation deferred to a 3-6 line block at the bottom. Ordering by what the human does with it inverts that, and the property the layout now holds explicitly — answer the closing question from the first screen without reading a code excerpt — is what every judgment about placement is made against. Evidence is appended rather than collapsed because Claude Code renders reports in a terminal, where a `<details>` block does not collapse; omitting it for "Noted" findings costs nothing, since the Step 6 record commit carries the full set to the branch regardless. The deferral posture was backwards in a way that compounds: a finding got recommended for `/capture-task` because its fix looked like a bigger change, including when the session's own work caused it, which is exactly the case where the session holding the change's context is the cheapest place the defect will ever be fixed — deferring buys a full context rebuild in a future session on top of the same fix. Size is therefore explicitly disqualified as grounds, and `/capture-task` narrows to two named cases, a pre-existing bug whose root cause needs investigation this change has no grounds to run or a design tradeoff deserving its own decision, with the recommendation stating which. Naming `/capture-task` as a destination is new coupling, hence the tracker fork-point. One stale claim in the README blurb is corrected while adjacent: it said the chair "verifies each against the actual code", which contradicts Step 3 — triage judges from context and defers deep verification to the findings the human selects.
- **Adaptation notes**: The `CLAUDE.md` rule is one bullet in Standards, taken verbatim or reworded to the instance's register; an instance whose sessions close through a fixed template (a PR body, a ticket comment) states that surface as the point-of-use exception rather than dropping the rule. Instances that forked `review-board` apply the three changes independently — they touch Part B of `output-format.md`, Step 3's disposition list, and Step 4's framing, and none of them touch the reviewer-agent contract in Part A, so forked checklists and the five `agents/review-*.md` definitions need no edits. An instance that added report sections of its own (compliance attestations, a sign-off block) places them below "Process notes" and above the evidence appendix, since the decision bullets own the first screen by construction. Instances whose captures live in a tracker rather than `docs/tasks/` name that destination in Step 3 per the new fork-point. An instance under a compliance regime that requires full evidence in every report keeps the appendix but extends it to the "Noted" findings too, rather than reverting the ordering — the ordering is what makes the report answerable, and the appendix is where length belongs either way.

## v1.0.3 — 2026-07-29

- **What**: Fixes two independent defects in the `guard-context-edit` hook. Governance is now scoped to the repository — a gated file must sit under `$CLAUDE_PROJECT_DIR`, the session's cwd, or `~/.claude`, or else share a git common directory with the session's checkout, with `node_modules` and `~/.claude/plugins/` carved back out — and a subagent's skill-load marker now resolves against the root session transcript as well as the agent's own, so a session that loads `curate-context` or `domain-modeling` before it delegates covers the agents it spawns. A load is now recognized as a structured transcript record rather than as a substring: an assistant `tool_use` block named `Skill`, or one of the two shapes a slash command is recorded in. Paths are canonicalized through `realpath` before any comparison, each transcript is scanned separately instead of concatenated, and a transcript that exists but cannot be read now fails open rather than blocking. The `CLAUDE.md` bullet describing the gate is rewritten in place to carry the inheritance affordance, so a session knows to load the owning skill before delegating rather than discovering it from a blocked edit.
- **Why**: the hook matches on basename, and a basename belongs to no project, so nothing stopped it from following a session off the repo: a throwaway `CONTEXT.md` in the session scratchpad, a `/tmp` note named `architecture.md`, a `README.md` in an unrelated checkout, and every vendored `node_modules/*/README.md` all blocked and demanded a full curation session for a file no context discipline governs — the scratchpad case being the one that fires daily, since sessions are instructed to put temp files there. Scoping by containment alone proved to be the wrong shape twice over, and both corrections came out of a review board on the first attempt. A worktree is a _sibling_ of the main checkout under `$HOME/Code/.worktrees/<project>/<branch>`, not a child, so lexical roots leave the other checkout of the same repository ungated — reproduced by executing both revisions against one `CLAUDE.md` write from a main checkout into its worktree, blocked before the change and allowed after, which is precisely the state `implement-task` occupies between `gwt-add.sh` and `EnterWorktree`. Git identity settles it without shelling out: a main checkout has a `.git` directory, a worktree has a `.git` file pointing at `<main>/.git/worktrees/<name>`, and both reduce to the same common directory, so two checkouts of one repository are one governance domain while an unrelated checkout stays released. Separately, `path.resolve` is purely lexical, so the canonical spelling the session reports for its cwd (`/private/tmp/...` on macOS) and the symlinked spelling a model may write (`/tmp/...`) compare unequal and drop governance for an entire tree; `realpath` on the longest existing prefix fixes that while still admitting a `Write` to a file that does not exist yet. The subagent half was invisible from the code: Claude Code writes each subagent's conversation to its own file beneath `<dir>/<session-id>/subagents/` while the session's own transcript is `<dir>/<session-id>.jsonl`, and the hook read only the path handed to it, so an orchestrator's skill load was unreadable to every agent it spawned. Confirmed against a real board run whose session transcript carries three skill markers and whose five subagent transcripts carry none, and by executing the hook on one `CLAUDE.md` edit twice: exit 0 under the session transcript, exit 2 under the subagent's. Any delegated wave whose payload is context edits therefore could not run at all. The escape hatch was worse than the block — a subagent can call the Skill tool and the marker does land in its own transcript (verified against an agent that loaded `tdd`), but `curate-context` and `domain-modeling` are human-in-the-loop disciplines and a subagent has no human to gate on, so self-loading satisfies the guard by discarding the thing it protects; agents whose tool list omits `Skill` had no recovery at all and simply burned turns retrying a denied edit. The derivation pattern must not pin the segment count after `subagents/`: a directly spawned agent sits at `subagents/agent-<id>.jsonl` but a workflow-spawned one sits at `subagents/workflows/wf_<id>/agent-<id>.jsonl`, and a pattern matching only the flat shape left the defect live for the workflow case — 212 of the 1,010 subagent transcripts on the development machine, or 21%, and exactly the delegation shape most likely to carry a wave of context edits. The corrected pattern derives an existing root session for all 1,010, and derives into `subagents/` for none of them, so a sibling agent's transcript is still never read directly. Reading the root session transcript also forced the marker itself to get stricter, because substring matching cannot tell a load from a mention and the widening would otherwise have spread every false-pass across a whole session: writing this guard's own test fixture — a file whose text contains `<command-name>/curate-context</command-name>` — put that string in the session transcript and switched the guard off for the remainder of that session. A load is therefore matched as a record now, which rejects file content, tool results, and quoted examples because each rides inside a record of some other shape. Both slash-command shapes must be accepted: built-in CLI commands are a `system` record with subtype `local_command`, while skill and custom commands are a `user` record whose `message.content` is a plain string, and a first pass that handled only the former would have stopped detecting every slash-command load and blocked the sessions that used one. Checked by replaying both the old and the new detection over all 1,397 transcripts on the development machine against eleven skill names: the structural check never fires where the textual one did not (so nothing is newly licensed), it detects 291 slash-command loads the record-only-`system` version would have missed, and the twelve textual matches it now rejects are all mentions rather than invocations. Two costs were fixed while the file was open: joining both transcripts before scanning allocated a second full copy of an append-only log that grows without bound (measured at roughly 28ms for a real 3.5MB+1.0MB pair and 97ms for a 15MB pair, against a process-spawn floor of 30-50ms), and swallowing every read error alike meant an `EACCES` on the root transcript — the only source that can carry an orchestrator's marker — blocked an edit the session was entitled to make, contradicting the fail-open posture the file's own header promises. Verified against 55 cases covering both directions, including both subagent layouts, both sibling-checkout directions, both slash-command shapes, a command tag quoted inside a Write payload, a symlinked spelling of a governed tree, an unreadable root transcript, a directory whose name merely prefixes the project root, the `docs/adr/`-before-`README.md` arm ordering, and all three fail-open edges.
- **Adaptation notes**: instances carrying the shipped hook take the new file wholesale. One behavior widening deserves a deliberate look: subagents can now edit context files whenever the spawning session loaded the owning skill, and an instance that wants delegated context edits forbidden outright drops the `transcriptsToSearch` derivation and keeps reading only `input.transcript_path`, accepting that such waves cannot run. Structural marker detection is the one change that can newly _block_ rather than newly allow, and it depends on transcript record shapes rather than on file text, so an instance running a Claude Code version that records a `Skill` invocation or a slash command differently sees legitimate loads stop being recognized; the check to run before adopting is a replay of both detections over that machine's own transcripts, confirming the structural one still fires everywhere a real load happened. An instance that keeps context docs in a genuinely separate checkout — a shared docs repository mounted elsewhere, with its own `.git` — adds that location to `GOVERNED_ROOTS`, since neither containment nor git identity reaches it; a `CLAUDE.md` symlinked in from a dotfiles repository needs nothing, because the link is edited through its in-repo path and canonicalization keeps it governed. Instances that forked the hook apply the changes by hand: the containment block belongs after the family dispatch rather than before it, so that an edit forwarded by the prefilter on a content match exits without touching the filesystem. Two vendored paths are excluded, `node_modules` and `~/.claude/plugins/` — the latter because admitting `~/.claude` whole to reach the user-global `CLAUDE.md` also swept in the marketplace and plugin-cache trees, 1,883 `README.md` files and 6 `CLAUDE.md` files on the development machine, none of them written by the project asked to curate them. Instances that commit generated `README.md` files under `dist/`, `build/`, or a vendored directory extend that list rather than reporting the block as a bug. Unchanged in this release: the `settings.json` prefilter still forwards on a literal case-variant list, so spellings outside it (`Context.md`, `Ui_Ux.md`, `docs/ADR/`) never reach the hook and stay ungated on case-insensitive filesystems — a pre-existing hole this release does not close. Closed in v1.0.6, which deletes the prefilter outright; the real count was six spellings, not three. An instance applying v1.0.3 and v1.0.6 in the same sitting takes the v1.0.3 hook body and skips the prefilter half of this note, since v1.0.6 removes the prefilter it describes.

## v1.0.2 — 2026-07-29

- **What**: Teaches the `guard-main` hook to exempt publishing an existing tag from its default-branch push block, so `git push origin vX.Y.Z` runs from `main` while every push that could move a branch stays blocked.
- **Why**: The hook blocked `git commit` and `git push` on the default branch with no exemption, but the release process this repo documents puts a `vX.Y.Z` tag on `main` — so the two rules contradicted each other and every release stalled on a step no AI session could perform. A tag ref moves no commits onto the branch, which is the only thing the guard exists to prevent, so the block was protecting nothing there. Found by hitting it while tagging v1.0.1. The exemption is deliberately narrow: the ref must resolve to a tag that already exists locally and must not also name a branch, so an invented or ambiguous name still blocks, and `--force`, `--force-with-lease`, `--mirror`, `--all`, `--follow-tags`, `--delete`, colon refspecs, and any `git commit` remain blocked. The exemption also stops reading shell redirections as refspecs: a real `git push origin v1.0.1 2>&1 | tail -3` arrives at the hook with `2>&1` among its tokens, which would fail the tag lookup and block a legitimate publish, so token scanning stops at the first `<`/`>` (characters git forbids in ref names). Verified against 37 cases covering both directions, including a name that is simultaneously a tag and a branch, a compound `git commit && git push origin <tag>` where the commit must still block, and every redirection form paired with a branch push to confirm redirections cannot smuggle one past the guard.
- **Adaptation notes**: Instances that kept the shipped `guard-main` hook take the new file wholesale; the change is purely permissive at one narrow point, so nothing that was blocked before becomes newly allowed except tag publishing. Instances that removed the hook, renamed their default branch, or forbid tagging from `main` as a matter of policy skip this release — the hook's block set is otherwise unchanged. An instance whose release process tags from a branch rather than `main` needs no change either, since the hook never guarded non-default branches.

## v1.0.1 — 2026-07-29

- **What**: Moves the Node runtime pin off `useNodeVersion` in `pnpm-workspace.yaml` onto `devEngines.runtime` in `package.json` (`onFail: "download"`), teaches `check-install.mjs` to hard-fail on drift between the pin sites and rewrites its remediation message, and makes `scripts/setup/gwt-add.sh` exit non-zero on a failed dependency install while becoming idempotent so re-running it repairs the worktree. `implement-task` gains the matching rules: a non-zero exit from `gwt-add.sh` stops the build, and the resume path checks for `node_modules` before trusting a listed worktree. Also repairs an unrelated pre-existing bug in both `gwt-add.sh` and `gwt-remove.sh`: their `main_root` assignment ran under `pipefail`, so outside a git repository the failing `git worktree list` propagated through the pipeline and `set -e` killed the script with a bare exit 128, leaving the friendly "not inside a git repository" branch below it permanently dead — both now exit 1 with that message.
- **Why**: pnpm 11 removed `useNodeVersion` and ignores the leftover key silently — no warning, and `pnpm config get use-node-version` still echoes the value back, so the pin read as configured while lifecycle scripts ran on whatever Node was ambient. Verified both directions with ambient Node 26.5.0 and the pin at 24.17.0: under pnpm 10.32.1 `preinstall` ran on 24.17.0, under pnpm 11.15.1 it ran on 26.5.0; `devEngines.runtime` supplies the pinned Node on both, so it is the mechanism that survives a pnpm major bump. `devEngines.runtime.version` is an exact version and must stay one: given a range, pnpm abandons its runtime resolution and installs the third-party `node` package from the npm registry instead, whose bin creation fails with `ENOENT` and whose setup script the build-script allowlist blocks, so lifecycle scripts silently run on the ambient Node — the original bug, reintroduced. One cost is accepted rather than fixed: npm reads `devEngines` before `preinstall` and treats `onFail: "download"` as `error`, so `npm install` on any Node but the pinned one dies with `EBADDEVENGINES` (reproduced on npm 11.17.0) instead of reaching the guard's pnpm-only message. The install is still stopped, which is the guard's actual job; only the diagnosis is worse, and the range spelling that would improve it breaks the pin outright. The guard now cross-checks `.nvmrc`, `engines.node`, and `devEngines.runtime.version` before it checks the machine, because a partial retarget otherwise surfaces as the wrong-Node message and sends the reader hunting through Homebrew symlinks and nvm sourcing for a repo bug. That message is also corrected: it no longer tells the reader to avoid upgrading pnpm (true only while the pin rode `useNodeVersion`; pnpm 9 ignores `devEngines` and does not self-switch to the `packageManager` pin, so upgrading is the fix there), no longer claims the required major is absent when the real problem is an old patch within it, and no longer describes `pnpm env use --global` as a silent no-op — it throws `ERR_PNPM_NO_GLOBAL_BIN_DIR` and is deprecated on pnpm 11 in favor of `pnpm runtime set node <version> -g`. The `gwt-add.sh` half is independent and is what turned a config problem into a debugging goose chase downstream: `if ! (cd "$target" && pnpm install); then` consumes the failure so `set -e` never fires, so the script printed "Worktree ready" and exited 0. Exiting 1 alone would have moved the bug rather than fixed it, since the worktree stays on disk and `implement-task`'s resume rule adopts any listed worktree without installing — hence the idempotent re-run and the `node_modules` check.
- **Adaptation notes**: Instances carrying the shipped pin delete `useNodeVersion` from `pnpm-workspace.yaml`, add the `devEngines` block to `package.json`, then run `pnpm install` and commit the regenerated `pnpm-lock.yaml` in the same change — pnpm turns `devEngines.runtime` into a `node: runtime:<version>` dependency, so the manifest edit alone desynchronizes the lockfile and every `--frozen-lockfile` install fails with `ERR_PNPM_OUTDATED_LOCKFILE`, which is CI's default. Retargeting the Node version therefore touches four sites: `.nvmrc` (the exact version), `engines.node` (the range `>=X.Y.Z <X+1`), `devEngines.runtime.version` (the same exact version — never a range, which silently disables the pin), and the regenerated lockfile; the guard hard-fails on drift between the first three and names the drifted field. Alpine and other musl-based images delete the `devEngines` block entirely and keep `.nvmrc` plus `engines.node` as the contract — `nodejs.org` publishes no musl build, so pnpm resolves the glibc tarball and the install dies at `preinstall` with a `not found` naming a binary that plainly exists (reproduced on `node:26-alpine` under pnpm 10.32.1 and 11.15.1; deleting the block installs cleanly). Budget for the download: ~57MB compressed and ~218MB unpacked on a cold pnpm store, fetched even when ambient Node already matches, so CI caches `$(pnpm store path)` and `nodejs.org` becomes a hard dependency of `pnpm install`. Treat the lockfile's `node@runtime:` block as hand-reviewed rather than generated — pnpm fetches those URLs verbatim from whatever host they name, so confirm each `url` host is `nodejs.org` and each `integrity` matches that release's `SHASUMS256.txt`; the block is a net improvement over `useNodeVersion`, which committed no integrity at all. An instance that added pnpm's `nodeVersion` key while chasing this removes it: `nodeVersion` sets the version pnpm _pretends_ when checking `engines`, so it makes engines checks pass against a fiction regardless of the Node actually running. An instance carrying `engineStrict: true` in `pnpm-workspace.yaml` (or `engine-strict=true` in `.npmrc`) flips it to `false` in the same change that deletes `nodeVersion`, or it ships a repo no developer can install on any Node but the pinned major — pnpm's own settings docs recommend pairing `nodeVersion` with `engineStrict` to stop contributors adding incompatible dependencies, so a docs-following instance has both, and `nodeVersion` was the only thing holding `engineStrict` harmless: delete it alone and the engines check falls through to the developer's ambient Node, and that check runs before pnpm switches to the `devEngines` runtime, so it blocks the very install that would have provisioned the pin. Measured on pnpm 10.34.1 with `engines.node` at `>=22.22.3 <23` and ambient Node 24.17.0: `engineStrict: true` fails every pnpm command with `ERR_PNPM_UNSUPPORTED_ENGINE`, `pnpm install` and `pnpm typecheck` alike, and provisioning the runtime first does not help because the check precedes the switch every time; `engineStrict: false` installs, fetches Node 22.22.3, and runs `pnpm exec` and `pnpm run` on it while the shell stays on 24.17.0. The cost is real and not recoverable: `engineStrict: false` gives up pnpm hard-blocking a _dependency_ that declares an incompatible engine, and getting that back means `engineStrict: true`, which reinstates the deadlock — `check-install.mjs` stays the backstop for the Node the repo actually runs on and is unaffected either way. Do not resolve this from pnpm's settings page, which claims a project's own `engines` field fails the install "regardless of this configuration"; that is not the observed behavior on 10.34.1, where the `engineStrict: false` install succeeds against a mismatched ambient Node. Instances that forked `gwt-add.sh` apply the exit-code and idempotency changes by hand; any automation reading its exit code gets stricter, not looser, so no caller needs relaxing.

## v1.0.0 — 2026-07-28

- **What**: Baseline release. The former two-layer meta-repo (`src/` payload + root tooling) is flattened into a single-layer GitHub template repository named `ai_starter`: the whole tracked tree is the payload. Ships the Claude Code process suite (skills, agents, guard hooks, permission registry), the design and domain doc skeletons, the setup scripts (`doctor.sh`, `check-install.mjs`, `gwt-add.sh`/`gwt-remove.sh`), a pnpm + Turborepo monorepo skeleton (`apps/*`, `packages/*`, pnpm-only installs enforced at `preinstall`), and the `sync-template` update channel this changelog feeds.
- **Why**: Dual-layer maintenance taxed every change twice and the layers drifted despite a lockstep mandate; flattening gives template and instances identical file paths, so updates diff and apply 1:1.
- **Adaptation notes**: Pre-baseline instances (created by copying the old `src/` payload) already share these paths. To adopt the update channel: add the template remote (`git remote add template git@github.com:donohoo13/ai_starter.git`), fetch it (`git fetch --no-tags template main`), copy the skill (`git checkout template/main -- .claude/skills/sync-template/`), and stamp `Template lineage: donohoo13/ai_starter, v1.0.0` into `CLAUDE.md`. One real fix to mirror: brace-form secret deny entries (`Read(**/.env.{local,...})`) do not enforce — verified empirically — so any instance carrying that form replaces it with individually enumerated entries as this baseline's `settings.json` does.
