# Changelog

Template releases, newest first. Each entry carries three parts: **what** changed, **why**, and **adaptation notes** for instances whose posture diverges from the shipped defaults (compliance regimes, external trackers, collapsed monorepos). A release is a git tag (`vX.Y.Z`) on `main` matching the entry heading; the `sync-template` skill in an instance walks unapplied entries oldest-to-newest (later releases assume earlier ones landed) and negotiates each into the instance's own posture. In an instance this file is template residue: `project-init` stamps the template lineage into `CLAUDE.md` from the top entry here, then deletes this copy.

## v1.0.3 — 2026-07-29

- **What**: Fixes two independent defects in the `guard-context-edit` hook. It now scopes governance to the repository — a gated file must sit under `$CLAUDE_PROJECT_DIR`, the session's cwd, or `~/.claude`, with `node_modules` carved back out — and it now resolves a subagent's skill-load marker against the root session transcript as well as the agent's own, so a session that loads `curate-context` or `domain-modeling` before it delegates covers the agents it spawns.
- **Why**: the hook matches on basename, and a basename belongs to no project, so nothing stopped it from following a session off the repo: a throwaway `CONTEXT.md` in the session scratchpad, a `/tmp` note named `architecture.md`, a `README.md` in an unrelated checkout, and every vendored `node_modules/*/README.md` all blocked and demanded a full curation session for a file no context discipline governs — the scratchpad case being the one that fires daily, since sessions are instructed to put temp files there. The session cwd is a governed root alongside `$CLAUDE_PROJECT_DIR` specifically because an `implement-task` worktree is a different path than the main checkout, and scoping to the project dir alone would have switched the guard off for every worktree build — trading a misfire for a silent hole. The subagent half is the worse defect and was invisible from the code: Claude Code writes each subagent's conversation to its own file at `<dir>/<session-id>/subagents/agent-<id>.jsonl` while the session's own transcript is `<dir>/<session-id>.jsonl`, and the hook read only the path handed to it, so an orchestrator's skill load was unreadable to every agent it spawned. Confirmed against a real board run whose session transcript carries three skill markers and whose five subagent transcripts carry none, and by executing the hook on one `CLAUDE.md` edit twice: exit 0 under the session transcript, exit 2 under the subagent's. Any delegated wave whose payload is context edits therefore could not run at all. The escape hatch was worse than the block — a subagent can call the Skill tool and the marker does land in its own transcript (verified against an agent that loaded `tdd`), but `curate-context` and `domain-modeling` are human-in-the-loop disciplines and a subagent has no human to gate on, so self-loading satisfies the guard by discarding the thing it protects; agents whose tool list omits `Skill` had no recovery at all and simply burned turns retrying a denied edit. One derivation step reaches the root session from any depth because agents spawned at depth 2 land in the same flat `subagents/` directory rather than nesting (checked across 793 subagent transcripts, 48 of them at depth 2). A sibling agent's transcript is deliberately not consulted: sharing markers across siblings would let one agent's load license an unrelated agent's edit. Verified against 37 cases covering both directions, including the scratchpad and worktree paths, a directory whose name merely prefixes the project root, marker leakage between siblings, the `docs/adr/`-before-`README.md` arm ordering, and all three fail-open edges.
- **Adaptation notes**: instances carrying the shipped hook take the new file wholesale — both changes are permissive at narrow points, and nothing previously allowed becomes blocked. Two behavior widenings are worth a deliberate look before adopting. First, subagents can now edit context files whenever the spawning session loaded the owning skill; an instance that wants delegated context edits forbidden outright drops the `transcriptsToSearch` derivation and keeps reading only `input.transcript_path`, accepting that such waves cannot run. Second, an instance that keeps its context docs outside the repository — a shared docs checkout mounted elsewhere, or `CLAUDE.md` symlinked in from a dotfiles repo — loses gating on those paths, since the containment check resolves the real path; add that location to `GOVERNED_ROOTS` in the same change. Instances that forked the hook apply both edits by hand: the roots check belongs immediately after path normalization and before the `.claude/skills/` exit, and the transcript derivation replaces the single `readFileSync` of `input.transcript_path`. The `node_modules` carve-out is the only vendored path excluded; instances that commit generated `README.md` files under `dist/`, `build/`, or a vendored directory extend that check rather than reporting the block as a bug. Unchanged in this release: the `settings.json` prefilter still forwards on a literal case-variant list, so spellings outside it (`Context.md`, `Ui_Ux.md`, `docs/ADR/`) never reach the hook and stay ungated on case-insensitive filesystems — a pre-existing hole this release does not close.

## v1.0.2 — 2026-07-29

- **What**: Teaches the `guard-main` hook to exempt publishing an existing tag from its default-branch push block, so `git push origin vX.Y.Z` runs from `main` while every push that could move a branch stays blocked.
- **Why**: The hook blocked `git commit` and `git push` on the default branch with no exemption, but the release process this repo documents puts a `vX.Y.Z` tag on `main` — so the two rules contradicted each other and every release stalled on a step no AI session could perform. A tag ref moves no commits onto the branch, which is the only thing the guard exists to prevent, so the block was protecting nothing there. Found by hitting it while tagging v1.0.1. The exemption is deliberately narrow: the ref must resolve to a tag that already exists locally and must not also name a branch, so an invented or ambiguous name still blocks, and `--force`, `--force-with-lease`, `--mirror`, `--all`, `--follow-tags`, `--delete`, colon refspecs, and any `git commit` remain blocked. The exemption also stops reading shell redirections as refspecs: a real `git push origin v1.0.1 2>&1 | tail -3` arrives at the hook with `2>&1` among its tokens, which would fail the tag lookup and block a legitimate publish, so token scanning stops at the first `<`/`>` (characters git forbids in ref names). Verified against 37 cases covering both directions, including a name that is simultaneously a tag and a branch, a compound `git commit && git push origin <tag>` where the commit must still block, and every redirection form paired with a branch push to confirm redirections cannot smuggle one past the guard.
- **Adaptation notes**: Instances that kept the shipped `guard-main` hook take the new file wholesale; the change is purely permissive at one narrow point, so nothing that was blocked before becomes newly allowed except tag publishing. Instances that removed the hook, renamed their default branch, or forbid tagging from `main` as a matter of policy skip this release — the hook's block set is otherwise unchanged. An instance whose release process tags from a branch rather than `main` needs no change either, since the hook never guarded non-default branches.

## v1.0.1 — 2026-07-29

- **What**: Moves the Node runtime pin off `useNodeVersion` in `pnpm-workspace.yaml` onto `devEngines.runtime` in `package.json` (`onFail: "download"`), teaches `check-install.mjs` to hard-fail on drift between the pin sites and rewrites its remediation message, and makes `scripts/setup/gwt-add.sh` exit non-zero on a failed dependency install while becoming idempotent so re-running it repairs the worktree. `implement-task` gains the matching rules: a non-zero exit from `gwt-add.sh` stops the build, and the resume path checks for `node_modules` before trusting a listed worktree. Also repairs an unrelated pre-existing bug in both `gwt-add.sh` and `gwt-remove.sh`: their `main_root` assignment ran under `pipefail`, so outside a git repository the failing `git worktree list` propagated through the pipeline and `set -e` killed the script with a bare exit 128, leaving the friendly "not inside a git repository" branch below it permanently dead — both now exit 1 with that message.
- **Why**: pnpm 11 removed `useNodeVersion` and ignores the leftover key silently — no warning, and `pnpm config get use-node-version` still echoes the value back, so the pin read as configured while lifecycle scripts ran on whatever Node was ambient. Verified both directions with ambient Node 26.5.0 and the pin at 24.17.0: under pnpm 10.32.1 `preinstall` ran on 24.17.0, under pnpm 11.15.1 it ran on 26.5.0; `devEngines.runtime` supplies the pinned Node on both, so it is the mechanism that survives a pnpm major bump. `devEngines.runtime.version` is an exact version and must stay one: given a range, pnpm abandons its runtime resolution and installs the third-party `node` package from the npm registry instead, whose bin creation fails with `ENOENT` and whose setup script the build-script allowlist blocks, so lifecycle scripts silently run on the ambient Node — the original bug, reintroduced. One cost is accepted rather than fixed: npm reads `devEngines` before `preinstall` and treats `onFail: "download"` as `error`, so `npm install` on any Node but the pinned one dies with `EBADDEVENGINES` (reproduced on npm 11.17.0) instead of reaching the guard's pnpm-only message. The install is still stopped, which is the guard's actual job; only the diagnosis is worse, and the range spelling that would improve it breaks the pin outright. The guard now cross-checks `.nvmrc`, `engines.node`, and `devEngines.runtime.version` before it checks the machine, because a partial retarget otherwise surfaces as the wrong-Node message and sends the reader hunting through Homebrew symlinks and nvm sourcing for a repo bug. That message is also corrected: it no longer tells the reader to avoid upgrading pnpm (true only while the pin rode `useNodeVersion`; pnpm 9 ignores `devEngines` and does not self-switch to the `packageManager` pin, so upgrading is the fix there), no longer claims the required major is absent when the real problem is an old patch within it, and no longer describes `pnpm env use --global` as a silent no-op — it throws `ERR_PNPM_NO_GLOBAL_BIN_DIR` and is deprecated on pnpm 11 in favor of `pnpm runtime set node <version> -g`. The `gwt-add.sh` half is independent and is what turned a config problem into a debugging goose chase downstream: `if ! (cd "$target" && pnpm install); then` consumes the failure so `set -e` never fires, so the script printed "Worktree ready" and exited 0. Exiting 1 alone would have moved the bug rather than fixed it, since the worktree stays on disk and `implement-task`'s resume rule adopts any listed worktree without installing — hence the idempotent re-run and the `node_modules` check.
- **Adaptation notes**: Instances carrying the shipped pin delete `useNodeVersion` from `pnpm-workspace.yaml`, add the `devEngines` block to `package.json`, then run `pnpm install` and commit the regenerated `pnpm-lock.yaml` in the same change — pnpm turns `devEngines.runtime` into a `node: runtime:<version>` dependency, so the manifest edit alone desynchronizes the lockfile and every `--frozen-lockfile` install fails with `ERR_PNPM_OUTDATED_LOCKFILE`, which is CI's default. Retargeting the Node version therefore touches four sites: `.nvmrc` (the exact version), `engines.node` (the range `>=X.Y.Z <X+1`), `devEngines.runtime.version` (the same exact version — never a range, which silently disables the pin), and the regenerated lockfile; the guard hard-fails on drift between the first three and names the drifted field. Alpine and other musl-based images delete the `devEngines` block entirely and keep `.nvmrc` plus `engines.node` as the contract — `nodejs.org` publishes no musl build, so pnpm resolves the glibc tarball and the install dies at `preinstall` with a `not found` naming a binary that plainly exists (reproduced on `node:26-alpine` under pnpm 10.32.1 and 11.15.1; deleting the block installs cleanly). Budget for the download: ~57MB compressed and ~218MB unpacked on a cold pnpm store, fetched even when ambient Node already matches, so CI caches `$(pnpm store path)` and `nodejs.org` becomes a hard dependency of `pnpm install`. Treat the lockfile's `node@runtime:` block as hand-reviewed rather than generated — pnpm fetches those URLs verbatim from whatever host they name, so confirm each `url` host is `nodejs.org` and each `integrity` matches that release's `SHASUMS256.txt`; the block is a net improvement over `useNodeVersion`, which committed no integrity at all. An instance that added pnpm's `nodeVersion` key while chasing this removes it: `nodeVersion` sets the version pnpm _pretends_ when checking `engines`, so it makes engines checks pass against a fiction regardless of the Node actually running. Instances that forked `gwt-add.sh` apply the exit-code and idempotency changes by hand; any automation reading its exit code gets stricter, not looser, so no caller needs relaxing.

## v1.0.0 — 2026-07-28

- **What**: Baseline release. The former two-layer meta-repo (`src/` payload + root tooling) is flattened into a single-layer GitHub template repository named `ai_starter`: the whole tracked tree is the payload. Ships the Claude Code process suite (skills, agents, guard hooks, permission registry), the design and domain doc skeletons, the setup scripts (`doctor.sh`, `check-install.mjs`, `gwt-add.sh`/`gwt-remove.sh`), a pnpm + Turborepo monorepo skeleton (`apps/*`, `packages/*`, pnpm-only installs enforced at `preinstall`), and the `sync-template` update channel this changelog feeds.
- **Why**: Dual-layer maintenance taxed every change twice and the layers drifted despite a lockstep mandate; flattening gives template and instances identical file paths, so updates diff and apply 1:1.
- **Adaptation notes**: Pre-baseline instances (created by copying the old `src/` payload) already share these paths. To adopt the update channel: add the template remote (`git remote add template git@github.com:donohoo13/ai_starter.git`), fetch it (`git fetch --no-tags template main`), copy the skill (`git checkout template/main -- .claude/skills/sync-template/`), and stamp `Template lineage: donohoo13/ai_starter, v1.0.0` into `CLAUDE.md`. One real fix to mirror: brace-form secret deny entries (`Read(**/.env.{local,...})`) do not enforce — verified empirically — so any instance carrying that form replaces it with individually enumerated entries as this baseline's `settings.json` does.
